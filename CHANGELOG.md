## Unreleased

* W4A8 kernels in packs: `pack build --w4a8` / `pack check --w4a8` (`pack.sweep_w4a8`), and `w4a8_op` falls back (the W4A16 kernels for the dual layout, a dense matmul with the dequantised weight for the compact one; `w4a8_op.FALLBACKS`, one warning) when a W4A8 kernel is in no pack and cannot be compiled, instead of raising. Those 192 / 256-request figures (0.82 / 0.77) were an artefact of the benchmark's memory budget, not of compute: `vllm_batch_sweep.py` fixes `gpu_memory_utilization = 0.55` of a 6 GB card, the two-layout W4A8 weights (2.0 GiB, against 1.0 for W4A16) leave too little KV cache for 256 sequences, so vLLM ran them in two waves (1.5x the decode steps in the profile: 5320 flash-attention launches against 3584). With `QF_GPU_UTIL=0.7` (a new environment variable of the script; 0.8 runs out of memory on this card for the QuantForge plugin), same session, two runs: Marlin 5642 / 7074 / 7480 / 7663 tokens/s at 64 / 128 / 192 / 256 requests, QuantForge W4A16 4823 / 5666 / 6470 / 6564, **W4A8 4890 / 6727 / 7963 / 8175: 1.06-1.07x of Marlin at 192-256 requests**, 0.95 at 128, 0.87 at 64. * 65..256 rows (decode at 65-256 concurrent requests): the row buckets are multiples of 32 there (96, 128, 160, 192, 224, 256; was 128, 256) with 32- or 64-row blocks (`torch_ops._mid_opts`, refined per shape by `tile_plan.plan_tile` when a pack is built, `QUANTFORGE_PLAN_MID=1`). A batch of 96 rows was padded to 128 and one of 192 to 256, 25-33 % of the arithmetic of a compute-bound GEMM thrown away, and the 128-row tile is a poor fit for the skinny sizes: kernel level, cold weights, 8960 x 1536 at 96 rows 263 -> 119 us, 4096 x 4096 150 -> 108, 1536 x 2048 54 -> 29, 1536 x 17920 244 -> 209; the very wide outputs (N >= 20000) keep the 128-row tile. vLLM, 1.5B, QuantForge W4A16 / Marlin at 96 / 128 / 192 / 256 requests: 0.63 / 0.69 / 0.70 / 0.85 -> 0.84 / 0.81 / 0.88 / 0.87; 3B 0.79 / 0.82 / 0.79 / 0.76 (average of two interleaved runs from a nine-model pack; the laptop throttled between sessions, ratios inside a session are what counts). The W4A8 hybrid op used the INT8 kernel from 17 rows on, where it has a ~170 us floor (1536 x 17920 at any M <= 128): its threshold is now 64 rows (`QUANTFORGE_W4A8_MIN_ROWS`; 32 requests 2054 -> 3361 tokens/s, 64 requests 3756 -> 5019); the W4A16 / INT8 crossover is shape dependent (INT8 wins from 96 rows for 1536 x 17920 and 2048 x 22016, from 224 for 8960 x 1536 and 4096 x 4096), a per-shape route would gain a few % more.
* Per-shape tile schedule for 16 rows too (`tile_plan.plan_tile(16, K, N)`, N > 2048): the decode rule takes a 64-deep K tile below N = 8192, which the cp.async copy of the 16 x bk activation tile cannot split evenly over the threads, so the exact-row kernels of M in {1, 2, 4, 8} (`valid-rows`) could not be built there and the op copied the activations to a padded buffer first (one more kernel). The planner times each schedule on the path the op takes for one row (padded copy included) and keeps one that wins by 3 %. Op in a CUDA graph, M = 1, cold weights (us, rule -> planned): 3584 x 3584 55.3 -> 43.0, 4096 x 6144 89.1 -> 77.8, 1536 x 17920 90.5 -> 85.0, 3072 x 16384 161.8 -> 151.6, 3584 x 4608 52.2 -> 50.2; 896 x 9728, 4096 x 4096, 4096 x 28672, 14336 x 4096 unchanged. vLLM from a nine-model pack (QuantForge / Marlin at 1 / 4 / 16 / 32 / 64 requests): 1.5B 0.936 / 0.934 / 0.933 / 0.905 / 0.847 (was 0.915 / 0.915 / 0.916 / 0.91 / 0.84), 3B 0.926 / 0.93 / 0.926 / 0.87 / 0.78 (unchanged: its layers are not among the shapes that gain). The 7B / 8B layers (qkv, o_proj of 3584 / 4096) are where it pays most but do not fit this 6 GB card for an end-to-end run.
* Per-shape tile schedule of the 32- / 64-row GEMMs (`tile_plan.plan_tile`, looked up by `torch_ops.default_opts`, decisions in the autotune cache and in kernel packs, `QUANTFORGE_NO_TILE_PLAN=1` disables): a sweep at balanced N (the earlier ones at N = 4096 were dominated by the 32-blocks-on-20-SMs imbalance) showed that the best tile depends on the shape; kernel level at 64 rows, cold weights: 1536 x 17920 136 -> 122 us, 3072 x 16384 243 -> 224, 4096 x 10240 190 -> 163, 896 x 9728 48 -> 42; at 32 rows 4096 x 6144 108 -> 86 us; a candidate must beat the default by 4 %, otherwise the default stays (2048 x 22016, 4096 x 6144 at 64 rows). End to end the gain is small because those shapes are a minor part of a model's step: from a nine-model pack, vLLM 64 requests 1.5B 0.836 -> 0.851 / 0.843 of Marlin, 3B 0.782 -> 0.782 / 0.776, 32 requests unchanged (0.91 / 0.87). What is left at 32-64 requests is the compute-bound mma loop itself (29 of 44 TFLOP/s against Marlin's 37), which needs the generated code, not the tile, to change.
* Atomic split-K for 17..64 rows (`atomic_plan.plan_atomic(rows=32|64)`, `W4A16GemmAtomic` M <= 64, the C++ op path for `M <= 64`): a block of the 32/64-row GEMM alternates dequantisation and mma, so the 16-24 column blocks of a narrow layer (one per SM) leave the tensor pipe idle (K = 4096: 20 blocks 88 us, 40 blocks 93 us for twice the work); cutting K gives two or three overlapping blocks per SM. Kernel level (cold weights): 8960 x 1536 83 -> 52 us at 32 rows and 96 -> 75 us at 64, 4864 x 896 33 -> 25 / 47 -> 32, 2048 x 2560 at 64 rows 44 -> 33; wide outputs lose and keep the plain kernel (the planner decides, >= 12 % gain). vLLM, QuantForge / Marlin at 16 / 32 / 64 requests: 1.5B 0.92 / 0.91 / **0.84** (64 requests was 0.81; 4893-4921 against 5813-5856 tokens/s), 3B 0.93 / 0.86 / **0.78** (64 requests was 0.76). Planners measure with CUDA events (`autotune.event_time`) instead of torch profiler sessions, the op only looks plans up and layers are planned when built (`atomic_plan.preplan`): profiler sessions started inside a layer's first call left later `torch.profiler` sessions of the process without GPU events (11 tests failed with a cold plan cache).
* From a pack only (JIT off, kernel and plan caches off), with the 32/64-row atomic plans: Qwen2.5-1.5B 129 / 507 / 1914 / 3356 / 4861 tokens/s at 1 / 4 / 16 / 32 / 64 requests against Marlin 141 / 553 / 2086 / 3680 / 5820 (0.92 / 0.92 / 0.92 / 0.91 / 0.84), Qwen2.5-3B 75 / 296 / 1130 / 1894 / 2771 against 81 / 320 / 1210 / 2193 / 3534 (0.93 / 0.93 / 0.93 / 0.86 / 0.78). `pack check` also fails when an optional kernel (atomic, f16-store, fold) is missing from the pack (`torch_ops.PACK_MISSES`), and isolates the plan cache so the decisions must come from the pack.
* Diagnosis of the 64-row gap (benchmarks/proto/bir_abl.cu ablations): with the dequantisation, the ldmatrix and the global B loads removed the register-B prototype still takes 75-80 us, so the limit is not ALU or memory; the compiler kernel is flat at 86-88 us from 20 to 32 blocks (one block per SM is latency bound), 33 TFLOP/s balanced for the prototype against 29 for the compiler.
* `quantforge-pack archive | install` (a nine-model pack is 9.4 MiB as .tar.gz; `install` takes a file or an https URL and refuses members that escape the directory) and `quantforge-doctor` runs a probe kernel from the pack when `quantforge-opt` is absent. The wheel (108 KB) installed into a clean venv runs the pack: `quantforge-pack install`, `quantforge-doctor` ok.
* Kernel packs (`quantforge.pack`, `e2e.pack_key` / `pack_dirs` / `KernelUnavailable`, `torch_ops._dense_impl`): a directory of ready-made kernels (`kernels/<key>.so`, PTX inside, linked only against libcuda), the measured plans (`plans.json`) and the prebuilt C++ torch runtime (`ext/<tag>/quantforge_rt.so`) lets a machine without LLVM / `quantforge-opt` / `nvcc` run the model: `python -m quantforge.pack build | ext | check`, `QUANTFORGE_PACK`, `QUANTFORGE_PACK_RECORD`, `QUANTFORGE_NO_JIT`. The pack key hashes the target, the pipeline options and the IR (no toolchain fingerprint). A shape missing from every pack falls back to a dense torch path (warning once, counted in `torch_ops.DENSE_FALLBACKS`) instead of failing; the planners (K-fold, atomic split-K) do not measure or cache anything without a toolchain. `pack build` plans first and records in a second process (kernels a planner builds while measuring stay in the process caches and would otherwise be missing from the pack; found by checking a nine-model pack, which had five gaps). Qwen2.5-0.5B: 110 kernels, 5.9 MiB; 1.5B: 104 kernels, 5.7 MiB; nine models (Qwen2.5 0.5-7B, Llama-3.x, Mistral-7B, Phi-3.5): 686 kernels, 38 MiB, no gap for any row count with the JIT off. Qwen2.5-3B from the pack: 75 / 297 / 1134 / 2704 tokens/s (Marlin 82 / 320 / 1214 / 3560, ratio 0.91 / 0.93 / 0.93 / 0.76). vLLM decode of the 1.5B from a pack only (JIT off, kernel cache off): 129 / 506 / 1917 / 4757 tokens/s at 1 / 4 / 16 / 64 requests (Marlin 141 / 553 / 2082 / 5871).
* Negative result, 64-row kernels: a wider sweep (`benchmarks/sweep_skinny64.py`, 2 warp-tile-m x 2 block-tile-n x 3 warp-tile-n x 3 K tiles x 3 stage counts) at 4096 x 4096 found 86.1 us at best against 87.4 us for the current schedule (Marlin 58.3 us), so the 0.67 gap of the 64-row kernels is not a tile-shape problem. Two further hypotheses were measured and refuted: (1) too few blocks (ncu: 32 blocks on 20 SMs, 13 % warps active, tensor pipe 52 % busy): `split-k=2..8 epilogue=atomic-add` with the 64-row tile is correct (error 5e-6) but 92-110 us against 88.6 us for the plain kernel; (2) L2 traffic of the activation tile (every block re-reads the whole 64 x K tile): 256-column blocks, which halve it, run in 100-150 us. Marlin reaches 84 % of the fp16 mma peak here (37 of 44 TFLOP/s), the compiler 55 %; the rest is in the instruction schedule of the dequantize / mma inner loop, not in the launch shape. SASS of the 64-row kernel (150 registers): per K tile and warp 64 HMMA against ~340 other instructions (the dequantized f16 B tile goes global -> registers -> dequantize -> STS -> LDSM, three barriers per iteration), so dequantization and mma alternate instead of overlapping. Double buffering cannot hide it at this size: `smem-stages=2` with a 64-deep K tile does not fit the 48 KiB static shared memory (26.6 KB per stage) and silently falls back to one stage (identical SASS, 85.9 vs 86.3 us); with 32-deep tiles it does fit and gains 16 % over its own single-stage schedule (105.5 -> 89.0 us) but not over the 64-deep tile (86 us). Ideas left, all in the code generator: dequantize in registers from the packed tile (Marlin) so the B tile never visits shared memory as f16, or a persistent stripe schedule that balances the 32 blocks over 20 SMs. Bound on the first idea, measured with the hand-written register-B prototype of `PIPELINE.md` run at 64 rows (4096 x 4096, cold weights, best of KS = 1/2/4/8): 76.8 us, i.e. 12 % under the compiler (86-88 us) and still 1.3x Marlin (58.3 us); at 32 rows 56.3 against 58.8 us for the compiler (Marlin 50.9). A full rewrite of the dequantization code generator would therefore buy about 12 % on the 64-row kernels (roughly +4 % of the end-to-end decode at 64 requests) and not close the gap to Marlin, so it is not done.
* `epilogue=atomic-add` with `split-k=S` (`quantforge-fuse-epilogue`, `e2e.W4A16GemmAtomic`, `atomic_plan.py`): the K reduction of a decode GEMM is cut over S blocks that add their [16 x bn] partial results with `red.global.add.f32` to a zeroed f32 buffer; the partial buffer, its device allocation and the reduce kernel are gone (one kernel, nothing allocated per call, so it can be captured in a CUDA graph; the float summation order varies from run to run). The C++ op uses it for the long-K narrow layers (`down_proj`, K / N >= 2.5, N <= 2048) at ANY 1..16 rows where the planner measures it faster than the plain kernel (cached per GPU and shape; no weight copy, unlike K-folding, which only serves M * S <= 16 rows). Kernel level, cold weights, 16 rows: 8960 x 1536 60 -> 46 us (0.62 -> 0.89 of Marlin), 4864 x 896 26.7 -> 24.3 us (0.60 -> 0.64); 1536 x 1536 and 896 x 896 do not gain and keep the plain kernel. vLLM decode on Qwen2.5-1.5B, plugin / Marlin at 1 / 4 / 16 / 64 requests: 0.92 / 0.875 / 0.857 / 0.81 -> 0.92 / 0.92 / 0.92 / 0.81 (tokens/s at 4 / 16 requests 485 / 1796 -> 509 / 1925; 64 requests use the 64-row kernels and are unchanged). `QUANTFORGE_NO_ATOMIC=1` turns it off.

* The decode K tile is 32 also for N = 20480 .. 25600 (`_decode_opts`): 10-14 % faster there (2048 x 20480: 136.7 -> 124.3 us, 4096 x 24576: 328 -> 302 us), found by a grid over (K, N) that showed the wave arithmetic (32-deep tiles run in 2 waves of 96 blocks, 128-deep in 3 of 80). The first version of this band also covered N = 8192 .. 9728 and gained only 1-6 %, less than the padded activation copy those kernels need (`valid-rows` requires a cp.async copy of the activation tile and a 16 x 32 tile is too small for 256 threads); a compiler change that let uneven tiles use cp.async made the 32-deep kernels 36 % SLOWER (133 -> 181 us for 4096 x 11008) and was reverted. `_kernel_f16` now falls back to the padded kernel when the exact-row kernel cannot be built: N = 10240 .. 12288 (Llama-7B's 11008) raised an error at M = 1, 2, 4, 8 before.

* K-folded GEMM without the padded activation copy (`torch_ops._kernel_fold`, the `foldvr` kernel): the kernel for exactly `M * S` rows of a 16-row tile (`valid-rows`, cp.async zero-fill), the f32 accumulator keeps 16 rows. Kernel level, cold weights, 1 row: 1536 x 1536 (fold 3) 13.6 -> 10.7 us (0.70 -> 0.90 of Marlin), 896 x 896 (fold 7) 7.9 -> 6.3 us (0.74 -> 0.92); 4864 x 896 (fold 2) 0.76 -> 0.81. 8960 x 1536 (fold 7) keeps the copy: its 10752 columns only allow a 32-deep K tile, and the 64-deep one that cp.async needs measured 57 us against 45. A sweep of the schedule options of four folded shapes found nothing (the default is within 0-0.6 us of the best): what was left was the copy and the reduce kernel (~1.2 us each). End to end the effect is below the noise: vLLM decode on Qwen2.5-1.5B, plugin / Marlin 0.92 / 0.88 / 0.86 / 0.81 at 1 / 4 / 16 / 64 requests, the same as before (the narrow layers are ~6 % of the GEMM time of a decode step). `QUANTFORGE_NO_VALID_ROWS=1` turns it off.

* `valid-rows` for the one-copy W4A8 decode kernel too (`W4A8DecodeGemm.build(valid_rows=)`): no padded copy at M = 1, 2, 4, 8. Compact mode decode 269 / 3928 (0.5B), 115 / 1719 (1.5B), 69 / 1029 (3B) at 1 / 16 requests, 0.82-0.91x of Marlin.

* `valid-rows=R` (`quantforge-gpu-pipeline`, `quantforge-smem-promotion`, `quantforge-fuse-epilogue`): a kernel compiled for a 16-row tile serves an `[R, K]` activation tensor without a padded copy (cp.async zero-fill, stores of the missing rows skipped). The C++ op uses it for M = 1, 2, 4, 8: the unfolded INT4 layers are ONE kernel per decode call (qkv 5.4 us at M = 1, Marlin 6.4; gate / up 19.6 against 27.3 with warm weights). `QUANTFORGE_NO_VALID_ROWS=1` turns it off. vLLM decode vs Marlin: 0.5B 0.95 / 0.95 / 0.92 / 0.88, 1.5B 0.91 / 0.88 / 0.86 / 0.81 at 1 / 4 / 16 / 64 requests.

* `epilogue=f16-store` (`quantforge-fuse-epilogue`, the `int8-dequant` machinery for an f32 accumulator; `e2e.W4A16GemmF16`): the INT4 GEMM writes f16 (+ f16 bias) itself. The C++ op uses it for plain GEMMs (no activation, INT4 group-wise): 2 kernels per decode call instead of 3-5 (qkv with bias 10.7 -> 6.5 us, Marlin 6.4), no f32 buffer; the other layouts use `kfold_reduce` for the bias + conversion. `QUANTFORGE_NO_F16STORE=1` turns it off. vLLM, QuantForge / Marlin decode on Qwen2.5-1.5B 0.74-0.87 -> 0.81-0.91, plugin prefill 20.6k -> 28.0k tokens/s; the W4A8 compact decode kernel uses it too (264 / 3952 on the 0.5B).

* `epilogue=int8-dequant` (`quantforge-fuse-epilogue`) and `quantforge.e2e.Int8GemmDq`: INT8 GEMM + `* sx[m] * sw[n] + bias[n]` -> f16 in ONE kernel with no int32 intermediate (1.29-1.81x cuBLAS fp16 for GEMM + dequantisation).
  `INT8W8A8Linear` uses it by default (`backend="quantforge"`, `quantize_model(..., int8_backend=)`): whole-model prefill 1.10x / 1.18x / 1.20x of fp16 for Qwen2.5-0.5B / Llama-3.2-1B / Qwen2.5-1.5B (cuBLASLt route: 0.91-1.08x). q/k/v and gate/up share one activation quantisation and one GEMM (`_Int8Shared`, 1-3 %); `int8_gemm_swizzle`: block rastering only for weights larger than the L2.

* Experimental compiler-generated INT8 GEMM (`quantforge.e2e.Int8Gemm`, `benchmarks/int8_gemm_probe.py`): `mma.m16n8k32.s8` through the existing pipeline, bit-exact for 129 schedules, 59-65 TOPS on large shapes, 1.1-1.7x cuBLAS fp16.
  Compiler: `arith.extsi` operands are folded into `vector.contract` (vectorization pass), new `thread-tile-k` pipeline option, `quantforge-overwrite-output` handles i32 accumulators; `quantforge-smem-promotion` recognises a transposed-B tile `[N-tile x K]` (48 of 180 block/warp combinations of the int8 GEMM gave wrong results before).

* `INT8W8A8Linear` / `quantize_model(fmt="int8_w8a8")` (cuBLASLt `_int_mm`) and `benchmarks/mma_peak.cu`: INT8 `mma` is 2.00x fp16 in hardware (88.2 vs 44.1 TOPS), 80-83 TOPS through cuBLASLt with a column-major B, but 0.90-1.07x of fp16
  for whole-model prefill; perplexity +0.33..0.41. Corrected the FP8 vs fp16 GEMM ratio to 1.9-2.1x (the fp16 baseline had been measured before the GPU reached its sustained clocks).

* Experimental `split-k=S` pipeline option (`quantforge-tiling{split-k=S}`, `quantforge-gpu-pipeline`): the K reduction cut over a third grid axis with partial results and a reduce kernel. Correct (FileCheck + numerical tests)
  but off by default: faster only for long-K, narrow-N layers at 32 rows (14-23 %), slower for most shapes at 64 rows, behind K-folding at 16 rows. Results and diagnosis (`ncu`: Marlin uses 20 persistent blocks) in the blog and README.

* 32 / 64-row schedules: 32 / 64-column blocks for N <= 2048 (11-52 % faster at kernel level); `benchmarks/sweep_skinny_blocks.py`. K-fold: the epilogue (sum of the diagonal blocks + bias + f16) is one CUDA kernel
  in the C++ runtime (`kfold_reduce.cu`, op `w4a16_gemm_kfold`), 3 kernels per folded call instead of 5-7. vLLM, QuantForge / Marlin: Qwen2.5-0.5B 0.87-0.96, 1.5B 0.74-0.87 at 1-64 requests.
* A failed build of the C++ runtime now says why in its warning (it used to be cut to the compiler command).

* `docker/Dockerfile`: image with the compiler, torch and the package (optionally vLLM); `quantforge-doctor` and the torch op verified inside it with `--gpus all`.
* vLLM plugin works on vLLM 0.24.0, 0.25.1 and 0.34.0 (fixes for 0.34: `use_batch_invariant`, the new `is_layer_skipped` keyword); the slow generation test now fails, instead of skipping, when only the plugin fails.
* vLLM plugin: needs vLLM >= 0.24 (the `auto_gptq` / `auto_awq` classes it extends are in 0.24-0.34.0 and absent before); with an older or missing vLLM it now warns once
  instead of registering nothing silently.

## 0.3.0 (2026-11-21)

* The op processes inputs of more than 2048 rows in chunks (bounded f32 temporary: Qwen2.5-3B could not start under vLLM on a 6 GB card because of the 8192-token profiling pass). `QUANTFORGE_KFOLD_BUDGET_MB` caps the extra memory of K-folding.
  Checked in vLLM: TinyLlama-1.1B act-order GPTQ (0.76-0.91 of Marlin), Qwen2.5-3B (0.87-0.88).

* vLLM plugin reads GPTQ 8-bit (`quant.from_gptq8`, act-order included) and AWQ 4-bit checkpoints; Qwen2.5-0.5B throughput vs the matching Marlin method: AWQ 0.81-0.89, GPTQ-Int8 0.85-0.93.

* Width-aware default schedules: `_decode_opts` (32 / 64-column blocks for N <= 2048) and `_skinny_opts` (17..64 rows, shape dependent); `torch_ops.default_opts`
  is shared with `benchmarks/compare_marlin.py` (its non-autotuned mode used an empty schedule for M > 16, not the op's). vLLM, QuantForge / Marlin: 0.80-0.88 at 1-16 requests, 0.73-0.80 at 64.

* `quantforge.kfold`: K-folding for long-K, narrow-N decode layers (`QuantLinear.enable_kfold()`, `nn.enable_kfold(model)`, `kfold=` in `quantize_model` / `load_quantized_checkpoint`,
  on by default in the vLLM plugin): +9 % (Qwen2.5-0.5B) / +15 % (1.5B) vLLM throughput at 1-4 requests, ~0.85x of Marlin there.

* vLLM plugin (`quantization="quantforge"`, entry point `vllm.general_plugins`): GPTQ 4-bit checkpoints on the QuantForge kernels; 70-80 % of Marlin's
  throughput on Qwen2.5-0.5B / 1.5B. `FP8W8A8Linear` / `quantize_model(fmt="fp8_w8a8")` (cuBLASLt FP8 tensor cores; quality good, no whole-model speed-up).

* GPTQ: calibration token norms are capped at 10x the median in the Hessian (`token_clip=10`), which removes a failure on models
  with a massive-activation layer (Llama-3.2-1B: GPTQ was worse than RTN on the whole Wikitext-2 test split, 24.08 against 22.28;
  now 20.21). A slow regression test (`test/E2E/test_gptq_real_model.py`, `QUANTFORGE_SLOW_TESTS=1`) guards the broken windows.
* Decode: K tile 32 for 10240 <= N <= 12288 (1 x 4096 x 11008: 149.5 -> 135.7 us, 0.93x Marlin); autotune candidates version 3.
* Benchmarks: `arc_eval.py`, `decode_repeat.py`, `kernel_repeat.py`, `ppl_per_window.py`; the comparison JSON is now
  `compare_baselines_rtx4050_sm89.json`.
