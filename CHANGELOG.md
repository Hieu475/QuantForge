## 0.5.0 - 2026-11-23

Mixture-of-experts support, extensions for many torch / Python versions.

* Negative results after the rotation (`research/`): (1) a per-layer choice of the rotation (identity / random sign flips / magnitude-interleaved channel permutation before the Hadamard blocks, picked by the layer-output error on calibration tokens, `research/rotation_search.py`): wikitext PPL 13.612 against 13.606 for the fixed Hadamard on Qwen2.5-1.5B (online round-to-nearest): nothing to gain from a search over cheap candidates; what is left of the gap to fp16 is the 4-bit weights (GPTQ takes it from 13.4 to 12.3), not the basis. (2) FP8 (e4m3) activations instead of INT8 on the Ada tensor cores: not built. With the rotation the INT8 activations cost only +0.01 / +0.04 perplexity on top of the 4-bit weights (`rotation_ppl.py`, variants rot-w4 vs rot-w4a8), so there is no quality left to win, the FP8 and INT8 mma rates are the same on this chip, and LLVM 18's NVVM dialect has no FP8 mma (it would need inline PTX and a second fragment path in the compiler). (3) fp8 KV cache (`QF_KV=fp8` in `vllm_ppl.py` / `vllm_batch_sweep.py`): it works with the W4A8 path and doubles the KV capacity (90,385 -> 170,670 tokens on the 6 GB card), but vLLM's default KV scale of 1.0 breaks Qwen2.5 (PPL 12.33 -> 24.96; the Marlin GPTQ checkpoint goes 13.64 -> 28.73 the same way), so it is not recommended without calibrated scales, which are vLLM's attention business and not something these GEMM kernels touch.
* **W4A8 rotation**: block-Hadamard (128) rotation of weights and activations. `quantization="quantforge_w4a8"` (online) rotates by default (`quantforge_w4a8_plain` = the old method); `benchmarks/make_w4a8_checkpoint.py --rotate` runs GPTQ in the rotated basis (`gptq.rotate_hessian`) and marks the checkpoint `"rotated": true`. Wikitext-2 PPL in vLLM, Qwen2.5-1.5B: online 13.949 -> 13.395, GPTQ 12.864 -> 12.331 (fp16 11.932, GPTQ W4A16 12.605); 0.5B online 23.148 -> 21.195. New CUDA kernels `hadamard128` and `quantize_rows_rot` (`act_quant.cu`), op flag `w4a8_hybrid(..., rotate)`, `W4A8Linear.rotate`. Throughput against Marlin (1.5B, GPTQ checkpoint): 0.92 / 0.93 / 0.97 / 0.98 / 1.01 / 1.11 / 1.16 at 1 / 16 / 32 / 64 / 128 / 192 / 256 requests (unrotated: 0.95 ... 1.18). Found while testing it: vLLM's compile cache is keyed by the quantisation name, not by environment variables, so an env switch that changes the traced graph silently reuses the other graph (wrong results, PPL 1e7); a custom op's fake must return the real output's strides (`empty_like` of a non-contiguous input does not).\n* W4A16 op: the activation rows of 65..256-row calls are padded with one CUDA kernel (`pad_rows_cuda`, `act_quant.cu`) instead of `constant_pad_nd` (3 small launches); no measurable change in the GEMM times (within noise). Negative results recorded while looking for the 0.74-0.80x of the exact W4A16 path at 96-256 rows: independent of the KV-cache fraction, not a wave-quantisation effect (split-K at 128 rows: 165 us vs 155 us), both kernels latency-bound (ncu: Marlin 115 us at 50 % DRAM, ours 154 us at 36 %); what is left is a weight format whose B fragments go from global memory straight to registers.
* MoE decode in vLLM, re-measured after the f16 swiglu output (four interleaved rounds at 16 and 32 requests): 0.96 / 0.95 / 0.95 / 0.93x of Marlin MoE at 1 / 8 / 16 / 32 requests. The "0.66x at 32 requests" of the first version was a KV-cache artifact (its f32 intermediate buffer shrank the KV cache and vLLM preempted), and the long search for a kernel-level cause of that gap (nsys, ncu, micro-benchmarks, real-routing replay) was chasing it.
* MoE prefill: 0.58x -> 0.88x of vLLM's Marlin MoE (OLMoE-1B-7B, 16 x 1275-token prompts: 6873 -> 10616 tokens/s; decode unchanged at ~0.93-0.97x). (1) `quantforge.swiglu_out`: the swiglu epilogue can store `silu(gate) * up` into its own f16 [M, N/2] argument (`FuseEpiloguePass`; `GroupedGemm(kind="swiglu16")`), so the f32 gate/up buffer and the cast kernel are gone and the token chunks grow from 256 to 512 (every chunk reads all the experts again). (2) Own schedules for the grouped 32 / 64 / 128-row kernels (`moe._opts`): the dense rule used block-m 64 inside 128-row problems (weights read twice) and the wrong warp tiles; sweeps with the read-only flush found K tile 64, one stage, look-ahead 1, 128-column blocks, 17-27 % faster (gate/up 1414 -> 1029 us at 256 tokens with a 64-row tile). (3) Row tile 16 / 32 / 64 by rows per expert (128 rows never won). Found by measuring the regime that had never been measured: MoE prefill.\n* W4A8 op: the per-token INT8 quantisation of the activations is one CUDA kernel of the C++ runtime (`runtime/act_quant.cu`, op `quantize_rows`) that also writes the zero rows up to the bucket, instead of a `torch.compile`d function (Triton / inductor needed at run time, compiled by the first big call) plus two padding copies when the row count is not a bucket. Bit-identical to the eager torch expression (the compiled one multiplies by a reciprocal and differs on exact .5 ties). 5-10 us per call at 20-100 rows: 20 x 8960 x 1536 60.4 -> 50.2 us (0.80 -> 0.96 of Marlin), 64 x 8960 x 1536 0.95 -> 1.07, 20 x 4096 x 4096 0.90 -> 1.00, 40 rows 0.83 -> 0.92. `QUANTFORGE_NO_NATIVE_QUANT=1` restores the old path. In vLLM (Qwen2.5-1.5B, two interleaved rounds against Marlin) the W4A8 path is now 0.95 / 0.96 / 0.99 / 0.99 / 1.04 / 1.13 / 1.18x at 1 / 16 / 32 / 64 / 128 / 192 / 256 requests.
* `scripts/memcheck_ops.py`: the production ops (W4A16 with the atomic split-K, K-fold and f16-store paths, W4A8 compact, MoE) over 15 row counts x 4 layer shapes of Qwen2.5-0.5B under `compute-sanitizer --tool memcheck` with the caching allocator off: 0 errors. (It is the check that found the 2-byte-vs-4-byte scale read of the INT8 planner inside vLLM.)
* `benchmarks/vllm_ppl.py`: perplexity of any model through vLLM (prompt log-probabilities of wikitext-2 windows). Qwen2.5-1.5B-Instruct: fp16 11.932, GPTQ-Int4 via Marlin 13.636, via `quantforge` 13.637, online W4A8 13.991. With this repository's GPTQ and the same calibration (wikitext-2 train, in-domain for the test split): W4A16 via `quantforge` 12.605, W4A8 checkpoint 12.851, i.e. +0.25 perplexity for the INT8 activations and integer group scales (Marlin cannot load the asymmetric W4A16 checkpoint). Tried and dropped: a K-major layout of the scales for the W4A8 *decode* kernel (no change in 60 us at 16 x 4096 x 4096; the kernel reads 77 % of the DRAM peak against 89 % for the W4A16 decode kernel with 14 % more instructions because its layout puts the nibbles of 8 rows in 8 different 4-byte loads: fixing it means storing the weights in the W4A16 layout and teaching the INT8 kernel to read it, a bigger change for 3-5 % end to end at 1-16 requests).
* Re-measured in vLLM (Qwen2.5-1.5B, two interleaved rounds) the exact W4A16 path against Marlin: 0.94 / 0.94 / 0.89 / 0.84 / 0.80 / 0.86 / 0.85 at 1 / 16 / 32 / 64 / 128 / 192 / 256 requests (the README had 0.93 / 0.93 / 0.91 / 0.85 / 0.81 / 0.88 / 0.87, measured several sessions earlier).
* **W4A8 faster than Marlin from 64 rows of GEMM** (`int8_plan.py`, `W4A8GemmDq(kmajor=True)`, `quant.kmajor_scales`, `benchmarks/compare_marlin_ops.py`). `ncu` on the INT8 kernel at 64 rows x 4096 x 4096: 67 % of the stall cycles are long-scoreboard (waiting on global loads); the rule of `w4a8_op` had been tuned on narrow layers (N <= 2048) and picked a 64 x 128 block with a 128-deep K tile for the square layers: 115 us. A sweep of 64 / 128 / 256-row blocks, 32 / 64 / 128 columns, K tiles 64 / 128 / 256, 2-8 warps, 1-3 stages and look-ahead 0-2 on eight shapes found 64 x 64 blocks with a 256-deep K tile and 16 x 32 warp tiles at 65 us (Marlin 61-67), 253 -> 145 us at 64 x 4096 x 11008, 65 -> 54 at 32 rows, 112 -> 103 at 128 rows, 183 -> 175 at 256. Because the best schedule depends on the shape it is measured once per (GPU, rows, K, N) like the W4A16 tile planner (`int8_plan.plan_int8`, 4 % margin, decisions in the autotune cache and in kernel packs, `pack.sweep_w4a8` and the plugin call `preplan`; `QUANTFORGE_NO_TILE_PLAN=1` disables). The integer group scales / zero points are also kept as int8 [K/128, N] (a second 3 % copy in the slots the compact layout leaves empty; with ONE extra zero row, because the look-ahead of the last K tile reads the next group's row): the 8 output channels of a thread are then adjacent bytes, 5 % faster. Op level against Marlin on 4096 x 4096: 0.95 / 1.02 / 1.06 / 1.15 / 1.17 / 1.22 at 32 / 64 / 96 / 128 / 192 / 256 rows (was 0.80 / 0.68 / 0.53 / 1.03 / - / 1.15); in vLLM (Qwen2.5-1.5B, two interleaved rounds) 0.94 / 0.96 / 0.97 / 0.98 / 1.01 / 1.08 / 1.13x of Marlin at 1 / 16 / 32 / 64 / 128 / 192 / 256 requests (was 0.95 / 0.96 / 0.95 / 0.97 / 0.96 / 1.06 / 1.06). The W4A16 op (exact Marlin numerics) is unchanged: 1.00 at 1-16 rows, 0.75-0.94 above.
* Lessons that cost time here: (1) a benchmark that flushes the L2 by *writing* (`zero_()`) leaves dirty lines whose write-back slows the next kernel: it showed the same rule at 147 us instead of 115 us and hid the real gap; flush by reading (`.max()`), as `autotune.event_time` does. (2) vLLM sets torch's default dtype to the model's while loading, so a planner's `torch.rand(...)` without `dtype=` made f16 scale tensors for a kernel that reads f32: out-of-bounds reads only inside vLLM (found with `compute-sanitizer` on the engine load: 0 errors afterwards). (3) `nsys` needs `--cuda-graph-trace=node` to see the kernels inside CUDA graphs.
* Prefill: the C++ op split long inputs into chunks of 2048 rows and copied every chunk's f16 result into the output (73 MB per chunk for N = 17920): 202 ms of `Memcpy DtoD` in a 16 x 1000-token prefill of Qwen2.5-1.5B (12 % of the GPU time). Exact chunks now write straight into their slice of the output (33 ms of copies left, the padded tail chunk): vLLM prefill 9380 -> 10289 tokens/s. **Correction:** the README claimed W4A16 prefill 1.1-1.15x of Marlin; measured in vLLM now it is 0.90-0.92x (GEMM time 1162 ms against 1050, and 0.9-1.04x per op at 384-2048 rows); W4A8 prefill is 1.07-1.14x. Found by comparing kernel-time profiles of the two prefill runs.
* **Mixture-of-experts** (`quantforge.moe`, `lib/Transforms/ExpertBatchPass.cpp`, `runtime/moe_kernels.cu`, `QuantForgeMoEMethod`): two compiler passes (`quantforge-expert-batch-launch`, `quantforge-expert-batch-pointers`; pipeline options `expert-problems`, `expert-roles`) turn any dense kernel into a grouped one (grid.z row-block problems, expert read from an `int32` array, per-expert weight pointers, padding problems return at once; lit test `gpu_pipeline_expert_batch.mlir`). `moe.moe_ffn_impl` = routing / gather / cast / combine CUDA kernels + grouped swiglu GEMM + grouped down GEMM, no host synchronisation (CUDA graphs capture it), tokens beyond 256 run in chunks (bounded f32 buffer: a first version with 1024-token chunks cost vLLM a third of its KV cache and was measured as 0.28x of Marlin at 32 requests for that reason alone). vLLM plugin: GPTQ / AWQ MoE layers (vLLM 0.25.1 and 0.34.0) reuse vLLM's loader and router. OLMoE-1B-7B GPTQ: identical text to vLLM's Marlin MoE, 0.94x of its decode speed at 1-16 requests, 0.66x at 32. `pack build / check` record and verify the grouped kernels (`pack.moe_dims`, `pack.sweep_moe`). ## 0.4.0 - 2026-11-22

First release prepared for PyPI under the distribution name `quantforge-llm` (the name `quantforge` belongs to an unrelated project; the import name stays `quantforge`).

* `quantforge.gptq_checkpoint.save_gptq` + `benchmarks/make_gptq_checkpoint.py` + `benchmarks/vllm_check_gptq_checkpoint.py`: quantise any Hugging Face causal LM with the repository's GPTQ and write a standard GPTQ checkpoint that vLLM loads. Llama-3.2-1B-Instruct (a family other than Qwen: GQA, tied head, no bias) in vLLM with the QuantForge kernels gives the same 289 greedy tokens as Hugging Face with the same weights, log-probability difference 0.001-0.003; from a pack alone 151 / 583 / 2119 / 5419 / 6791 / 7375 tokens/s at 1 / 4 / 16 / 64 / 128 / 256 requests (W4A8 online: 151 / 581 / 2137 / 5427 / 7565 / 8995). vLLM's Marlin refuses the checkpoint (it only loads symmetric GPTQ; this one keeps the zero points).
* W4A8 single-layout (`compact`) is now the default (`QUANTFORGE_W4A8_DECODE=w4a16` restores the two layouts): its decode kernel got a tile schedule for the single layout (`w4a8_op._decode_opts`: 256-deep K tile, 8-wide warp tiles, 32-/64-column blocks; cold weights, us, old -> new: 4096 x 4096 89.8 -> 57.5, 8960 x 1536 83.2 -> 51.8, 11008 x 2048 109.5 -> 76.7, 1536 x 1536 13.0 -> 10.3, 1536 x 17920 82.8 -> 80.0) and the 32- / 64-row INT8 kernel a better one (`_int8_opts`: 64-column blocks, 16 x 32 warp tiles, 256-deep K tile; 8960 x 1536 93 -> 54 us at 32 rows, 94 -> 60 at 64, 1536 x 1536 16.6 -> 11.5). vLLM, Qwen2.5-1.5B online W4A8, one weight copy (1.13 GiB, the two layouts took 2.04) / Marlin, two interleaved runs, at 1 / 16 / 32 / 64 / 96 / 128 requests: 0.95 / 0.96 / 0.95 / 0.97 / 0.95 / 0.96 (it was 0.78 / 0.79 / 0.77 / 0.84 / 0.91 / 0.95) and still 1.06 at 192-256.
* W4A8 kernels in packs: `pack build --w4a8` / `pack check --w4a8` (`pack.sweep_w4a8`), and `w4a8_op` falls back (the W4A16 kernels for the dual layout, a dense matmul with the dequantised weight for the compact one; `w4a8_op.FALLBACKS`, one warning) when a W4A8 kernel is in no pack and cannot be compiled, instead of raising. Nine-model pack with W4A8: 1566 kernels, 94 MiB, built in 191 s; from it alone Qwen2.5-1.5B W4A8 / Marlin at 1 / 16 / 64 / 128 / 192 / 256 requests 0.93 / 0.94 / 0.86 / 0.95 / 1.06 / 1.06 (`QF_GPU_UTIL=0.7`).
* W4A8 INT8 kernel for 96..256 rows (`w4a8_op._int8_opts`, buckets 96 / 128 / 160 / 192 / 224 / 256 instead of 128 / 256): the 128 x 128 block with 64 x 64 warp tiles of the large-batch schedule is a poor fit below ~512 rows; with 32 x 128 or 64 x 64 blocks (cold weights, us, default -> new) 8960 x 1536 at 128 rows 183 -> 108 and at 256 rows 186 -> 139, 1536 x 17920 at 128 rows 165 -> 138, at 256 rows 266 -> 243; the INT8 path now beats the W4A16 kernels at nearly every row count from 96 up (1536 x 17920 at 192 rows 207 against 314 us). vLLM, Qwen2.5-1.5B online W4A8 / Marlin (GPTQ) at 64 / 96 / 128 / 192 / 256 requests: 0.64 (before the 64-row threshold) -> 0.86 / 0.83 -> 0.94 / 0.89 -> 0.95 / 0.72 -> 0.82 / 0.73 -> 0.77 (5036 / 5934 / 6943 / 6372 / 6110 against 5877 / 6330 / 7302 / 7734 / 7903 tokens/s). Those 192 / 256-request figures (0.82 / 0.77) were an artefact of the benchmark's memory budget, not of compute: `vllm_batch_sweep.py` fixes `gpu_memory_utilization = 0.55` of a 6 GB card, the two-layout W4A8 weights (2.0 GiB, against 1.0 for W4A16) leave too little KV cache for 256 sequences, so vLLM ran them in two waves (1.5x the decode steps in the profile: 5320 flash-attention launches against 3584). With `QF_GPU_UTIL=0.7` (a new environment variable of the script; 0.8 runs out of memory on this card for the QuantForge plugin), same session, two runs: Marlin 5642 / 7074 / 7480 / 7663 tokens/s at 64 / 128 / 192 / 256 requests, QuantForge W4A16 4823 / 5666 / 6470 / 6564, **W4A8 4890 / 6727 / 7963 / 8175: 1.06-1.07x of Marlin at 192-256 requests**, 0.95 at 128, 0.87 at 64. (W4A8 is not the same numerics as Marlin's W4A16: INT8 activations, and round-to-nearest quantisation when the checkpoint is quantised on load: wikitext-2 perplexity of the 0.5B 23.7 against 20.5 for GPTQ W4A16, 21.1 with a GPTQ-quantised W4A8 checkpoint.) `QUANTFORGE_W4A8_DECODE=compact` (one copy of the nibbles, 1.13 GiB instead of 2.04 on the 1.5B) gives the same at 192 / 256 requests with the default 0.55 budget (7940 / 8150) and, with INT8 buckets of 32 and 64 rows added for it (17-95 rows were padded to 96), 2834 / 4909 / 5753 tokens/s at 32 / 64 / 96 requests; its decode at 1 / 16 requests is 0.78 / 0.79 of Marlin.
* 65..256 rows (decode at 65-256 concurrent requests): the row buckets are multiples of 32 there (96, 128, 160, 192, 224, 256; was 128, 256) with 32- or 64-row blocks (`torch_ops._mid_opts`, refined per shape by `tile_plan.plan_tile` when a pack is built, `QUANTFORGE_PLAN_MID=1`). A batch of 96 rows was padded to 128 and one of 192 to 256, 25-33 % of the arithmetic of a compute-bound GEMM thrown away, and the 128-row tile is a poor fit for the skinny sizes: kernel level, cold weights, 8960 x 1536 at 96 rows 263 -> 119 us, 4096 x 4096 150 -> 108, 1536 x 2048 54 -> 29, 1536 x 17920 244 -> 209; the very wide outputs (N >= 20000) keep the 128-row tile. vLLM, 1.5B, QuantForge W4A16 / Marlin at 96 / 128 / 192 / 256 requests: 0.63 / 0.69 / 0.70 / 0.85 -> 0.84 / 0.81 / 0.88 / 0.87; 3B 0.79 / 0.82 / 0.79 / 0.76 (average of two interleaved runs from a nine-model pack; the laptop throttled between sessions, ratios inside a session are what counts). The W4A8 hybrid op used the INT8 kernel from 17 rows on, where it has a ~170 us floor (1536 x 17920 at any M <= 128): its threshold is now 64 rows (`QUANTFORGE_W4A8_MIN_ROWS`; 32 requests 2054 -> 3361 tokens/s, 64 requests 3756 -> 5019); the W4A16 / INT8 crossover is shape dependent (INT8 wins from 96 rows for 1536 x 17920 and 2048 x 22016, from 224 for 8960 x 1536 and 4096 x 4096), a per-shape route would gain a few % more.
* Per-shape tile schedule for 16 rows too (`tile_plan.plan_tile(16, K, N)`, N > 2048): the decode rule takes a 64-deep K tile below N = 8192, which the cp.async copy of the 16 x bk activation tile cannot split evenly over the threads, so the exact-row kernels of M in {1, 2, 4, 8} (`valid-rows`) could not be built there and the op copied the activations to a padded buffer first (one more kernel). The planner times each schedule on the path the op takes for one row (padded copy included) and keeps one that wins by 3 %. Op in a CUDA graph, M = 1, cold weights (us, rule -> planned): 3584 x 3584 55.3 -> 43.0, 4096 x 6144 89.1 -> 77.8, 1536 x 17920 90.5 -> 85.0, 3072 x 16384 161.8 -> 151.6, 3584 x 4608 52.2 -> 50.2; 896 x 9728, 4096 x 4096, 4096 x 28672, 14336 x 4096 unchanged. vLLM from a nine-model pack (QuantForge / Marlin at 1 / 4 / 16 / 32 / 64 requests): 1.5B 0.936 / 0.934 / 0.933 / 0.905 / 0.847 (was 0.915 / 0.915 / 0.916 / 0.91 / 0.84), 3B 0.926 / 0.93 / 0.926 / 0.87 / 0.78 (unchanged: its layers are not among the shapes that gain). The 7B / 8B layers (qkv, o_proj of 3584 / 4096) are where it pays most but do not fit this 6 GB card for an end-to-end run.
* Per-shape tile schedule of the 32- / 64-row GEMMs (`tile_plan.plan_tile`, looked up by `torch_ops.default_opts`, decisions in the autotune cache and in kernel packs, `QUANTFORGE_NO_TILE_PLAN=1` disables): a sweep at balanced N (the earlier ones at N = 4096 were dominated by the 32-blocks-on-20-SMs imbalance) showed that the best tile depends on the shape; kernel level at 64 rows, cold weights: 1536 x 17920 136 -> 122 us, 3072 x 16384 243 -> 224, 4096 x 10240 190 -> 163, 896 x 9728 48 -> 42; at 32 rows 4096 x 6144 108 -> 86 us; a candidate must beat the default by 4 %, otherwise the default stays (2048 x 22016, 4096 x 6144 at 64 rows). End to end the gain is small because those shapes are a minor part of a model's step: from a nine-model pack, vLLM 64 requests 1.5B 0.836 -> 0.851 / 0.843 of Marlin, 3B 0.782 -> 0.782 / 0.776, 32 requests unchanged (0.91 / 0.87). What is left at 32-64 requests is the compute-bound mma loop itself (29 of 44 TFLOP/s against Marlin's 37), which needs the generated code, not the tile, to change.
* Atomic split-K for 17..64 rows (`atomic_plan.plan_atomic(rows=32|64)`, `W4A16GemmAtomic` M <= 64, the C++ op path for `M <= 64`): a block of the 32/64-row GEMM alternates dequantisation and mma, so the 16-24 column blocks of a narrow layer (one per SM) leave the tensor pipe idle (K = 4096: 20 blocks 88 us, 40 blocks 93 us for twice the work); cutting K gives two or three overlapping blocks per SM. Kernel level (cold weights): 8960 x 1536 83 -> 52 us at 32 rows and 96 -> 75 us at 64, 4864 x 896 33 -> 25 / 47 -> 32, 2048 x 2560 at 64 rows 44 -> 33; wide outputs lose and keep the plain kernel (the planner decides, >= 12 % gain). vLLM, QuantForge / Marlin at 16 / 32 / 64 requests: 1.5B 0.92 / 0.91 / **0.84** (64 requests was 0.81; 4893-4921 against 5813-5856 tokens/s), 3B 0.93 / 0.86 / **0.78** (64 requests was 0.76). Planners measure with CUDA events (`autotune.event_time`) instead of torch profiler sessions, the op only looks plans up and layers are planned when built (`atomic_plan.preplan`): profiler sessions started inside a layer's first call left later `torch.profiler` sessions of the process without GPU events (11 tests failed with a cold plan cache).
* From a pack only (JIT off, kernel and plan caches off), with the 32/64-row atomic plans: Qwen2.5-1.5B 129 / 507 / 1914 / 3356 / 4861 tokens/s at 1 / 4 / 16 / 32 / 64 requests against Marlin 141 / 553 / 2086 / 3680 / 5820 (0.92 / 0.92 / 0.92 / 0.91 / 0.84), Qwen2.5-3B 75 / 296 / 1130 / 1894 / 2771 against 81 / 320 / 1210 / 2193 / 3534 (0.93 / 0.93 / 0.93 / 0.86 / 0.78). `pack check` also fails when an optional kernel (atomic, f16-store, fold) is missing from the pack (`torch_ops.PACK_MISSES`), and isolates the plan cache so the decisions must come from the pack.
* Diagnosis of the 64-row gap (benchmarks/proto/bir_abl.cu ablations): with the dequantisation, the ldmatrix and the global B loads removed the register-B prototype still takes 75-80 us, so the limit is not ALU or memory; the compiler kernel is flat at 86-88 us from 20 to 32 blocks (one block per SM is latency bound), 33 TFLOP/s balanced for the prototype against 29 for the compiler.
* `quantforge-pack archive | install` (a nine-model pack is 9.4 MiB as .tar.gz; `install` takes a file or an https URL and refuses members that escape the directory) and `quantforge-doctor` runs a probe kernel from the pack when `quantforge-opt` is absent. The wheel (108 KB) installed into a clean venv runs the pack: `quantforge-pack install`, `quantforge-doctor` ok.
* Kernel packs (`quantforge.pack`, `e2e.pack_key` / `pack_dirs` / `KernelUnavailable`, `torch_ops._dense_impl`): a directory of ready-made kernels (`kernels/<key>.so`, PTX inside, linked only against libcuda), the measured plans (`plans.json`) and the prebuilt C++ torch runtime (`ext/<tag>/quantforge_rt.so`) lets a machine without LLVM / `quantforge-opt` / `nvcc` run the model: `python -m quantforge.pack build | ext | check`, `QUANTFORGE_PACK`, `QUANTFORGE_PACK_RECORD`, `QUANTFORGE_NO_JIT`. The pack key hashes the target, the pipeline options and the IR (no toolchain fingerprint). A shape missing from every pack falls back to a dense torch path (warning once, counted in `torch_ops.DENSE_FALLBACKS`) instead of failing; the planners (K-fold, atomic split-K) do not measure or cache anything without a toolchain. `pack build` plans first and records in a second process (kernels a planner builds while measuring stay in the process caches and would otherwise be missing from the pack; found by checking a nine-model pack, which had five gaps). Qwen2.5-0.5B: 110 kernels, 5.9 MiB; 1.5B: 104 kernels, 5.7 MiB; nine models (Qwen2.5 0.5-7B, Llama-3.x, Mistral-7B, Phi-3.5): 686 kernels, 38 MiB, no gap for any row count with the JIT off. Qwen2.5-3B from the pack: 75 / 297 / 1134 / 2704 tokens/s (Marlin 82 / 320 / 1214 / 3560, ratio 0.91 / 0.93 / 0.93 / 0.76). vLLM decode of the 1.5B from a pack only (JIT off, kernel cache off): 129 / 506 / 1917 / 4757 tokens/s at 1 / 4 / 16 / 64 requests (Marlin 141 / 553 / 2082 / 5871).
* Negative result, 64-row kernels: a wider sweep (`benchmarks/sweep_skinny64.py`, 2 warp-tile-m x 2 block-tile-n x 3 warp-tile-n x 3 K tiles x 3 stage counts) at 4096 x 4096 found 86.1 us at best against 87.4 us for the current schedule (Marlin 58.3 us), so the 0.67 gap of the 64-row kernels is not a tile-shape problem. Two further hypotheses were measured and refuted: (1) too few blocks (ncu: 32 blocks on 20 SMs, 13 % warps active, tensor pipe 52 % busy): `split-k=2..8 epilogue=atomic-add` with the 64-row tile is correct (error 5e-6) but 92-110 us against 88.6 us for the plain kernel; (2) L2 traffic of the activation tile (every block re-reads the whole 64 x K tile): 256-column blocks, which halve it, run in 100-150 us. Marlin reaches 84 % of the fp16 mma peak here (37 of 44 TFLOP/s), the compiler 55 %; the rest is in the instruction schedule of the dequantize / mma inner loop, not in the launch shape. SASS of the 64-row kernel (150 registers): per K tile and warp 64 HMMA against ~340 other instructions (the dequantized f16 B tile goes global -> registers -> dequantize -> STS -> LDSM, three barriers per iteration), so dequantization and mma alternate instead of overlapping. Double buffering cannot hide it at this size: `smem-stages=2` with a 64-deep K tile does not fit the 48 KiB static shared memory (26.6 KB per stage) and silently falls back to one stage (identical SASS, 85.9 vs 86.3 us); with 32-deep tiles it does fit and gains 16 % over its own single-stage schedule (105.5 -> 89.0 us) but not over the 64-deep tile (86 us). Ideas left, all in the code generator: dequantize in registers from the packed tile (Marlin) so the B tile never visits shared memory as f16, or a persistent stripe schedule that balances the 32 blocks over 20 SMs. Bound on the first idea, measured with the hand-written register-B prototype of `PIPELINE.md` run at 64 rows (4096 x 4096, cold weights, best of KS = 1/2/4/8): 76.8 us, i.e. 12 % under the compiler (86-88 us) and still 1.3x Marlin (58.3 us); at 32 rows 56.3 against 58.8 us for the compiler (Marlin 50.9). A full rewrite of the dequantization code generator would therefore buy about 12 % on the 64-row kernels (roughly +4 % of the end-to-end decode at 64 requests) and not close the gap to Marlin, so it is not done.
* `epilogue=atomic-add` with `split-k=S` (`quantforge-fuse-epilogue`, `e2e.W4A16GemmAtomic`, `atomic_plan.py`): the K reduction of a decode GEMM is cut over S blocks that add their [16 x bn] partial results with `red.global.add.f32` to a zeroed f32 buffer; the partial buffer, its device allocation and the reduce kernel are gone (one kernel, nothing allocated per call, so it can be captured in a CUDA graph; the float summation order varies from run to run). The C++ op uses it for the long-K narrow layers (`down_proj`, K / N >= 2.5, N <= 2048) at ANY 1..16 rows where the planner measures it faster than the plain kernel (cached per GPU and shape; no weight copy, unlike K-folding, which only serves M * S <= 16 rows). Kernel level, cold weights, 16 rows: 8960 x 1536 60 -> 46 us (0.62 -> 0.89 of Marlin), 4864 x 896 26.7 -> 24.3 us (0.60 -> 0.64); 1536 x 1536 and 896 x 896 do not gain and keep the plain kernel. vLLM decode on Qwen2.5-1.5B, plugin / Marlin at 1 / 4 / 16 / 64 requests: 0.92 / 0.875 / 0.857 / 0.81 -> 0.92 / 0.92 / 0.92 / 0.81 (tokens/s at 4 / 16 requests 485 / 1796 -> 509 / 1925; 64 requests use the 64-row kernels and are unchanged). `QUANTFORGE_NO_ATOMIC=1` turns it off.

* The decode K tile is 32 also for N = 20480 .. 25600 (`_decode_opts`): 10-14 % faster there (2048 x 20480: 136.7 -> 124.3 us, 4096 x 24576: 328 -> 302 us), found by a grid over (K, N) that showed the wave arithmetic (32-deep tiles run in 2 waves of 96 blocks, 128-deep in 3 of 80). The first version of this band also covered N = 8192 .. 9728 and gained only 1-6 %, less than the padded activation copy those kernels need (`valid-rows` requires a cp.async copy of the activation tile and a 16 x 32 tile is too small for 256 threads); a compiler change that let uneven tiles use cp.async made the 32-deep kernels 36 % SLOWER (133 -> 181 us for 4096 x 11008) and was reverted. `_kernel_f16` now falls back to the padded kernel when the exact-row kernel cannot be built: N = 10240 .. 12288 (Llama-7B's 11008) raised an error at M = 1, 2, 4, 8 before.

* K-folded GEMM without the padded activation copy (`torch_ops._kernel_fold`, the `foldvr` kernel): the kernel for exactly `M * S` rows of a 16-row tile (`valid-rows`, cp.async zero-fill), the f32 accumulator keeps 16 rows. Kernel level, cold weights, 1 row: 1536 x 1536 (fold 3) 13.6 -> 10.7 us (0.70 -> 0.90 of Marlin), 896 x 896 (fold 7) 7.9 -> 6.3 us (0.74 -> 0.92); 4864 x 896 (fold 2) 0.76 -> 0.81. 8960 x 1536 (fold 7) keeps the copy: its 10752 columns only allow a 32-deep K tile, and the 64-deep one that cp.async needs measured 57 us against 45. A sweep of the schedule options of four folded shapes found nothing (the default is within 0-0.6 us of the best): what was left was the copy and the reduce kernel (~1.2 us each). End to end the effect is below the noise: vLLM decode on Qwen2.5-1.5B, plugin / Marlin 0.92 / 0.88 / 0.86 / 0.81 at 1 / 4 / 16 / 64 requests, the same as before (the narrow layers are ~6 % of the GEMM time of a decode step). `QUANTFORGE_NO_VALID_ROWS=1` turns it off.

* `valid-rows` for the one-copy W4A8 decode kernel too (`W4A8DecodeGemm.build(valid_rows=)`): no padded copy at M = 1, 2, 4, 8. Compact mode decode 269 / 3928 (0.5B), 115 / 1719 (1.5B), 69 / 1029 (3B) at 1 / 16 requests, 0.82-0.91x of Marlin.

* `valid-rows=R` (`quantforge-gpu-pipeline`, `quantforge-smem-promotion`, `quantforge-fuse-epilogue`): a kernel compiled for a 16-row tile serves an `[R, K]` activation tensor without a padded copy (cp.async zero-fill, stores of the missing rows skipped). The C++ op uses it for M = 1, 2, 4, 8: the unfolded INT4 layers are ONE kernel per decode call (qkv 5.4 us at M = 1, Marlin 6.4; gate / up 19.6 against 27.3 with warm weights). `QUANTFORGE_NO_VALID_ROWS=1` turns it off. vLLM decode vs Marlin: 0.5B 0.95 / 0.95 / 0.92 / 0.88, 1.5B 0.91 / 0.88 / 0.86 / 0.81 at 1 / 4 / 16 / 64 requests.

* `epilogue=f16-store` (`quantforge-fuse-epilogue`, the `int8-dequant` machinery for an f32 accumulator; `e2e.W4A16GemmF16`): the INT4 GEMM writes f16 (+ f16 bias) itself.
