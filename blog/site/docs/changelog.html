0.5.0 - 2026-11-23#

Mixture-of-experts support, extensions for many torch / Python versions.

  • Negative results after the rotation (research/): (1) a per-layer choice of the rotation (identity / random sign flips / magnitude-interleaved channel permutation before the Hadamard blocks, picked by the layer-output error on calibration tokens, research/rotation_search.py): wikitext PPL 13.612 against 13.606 for the fixed Hadamard on Qwen2.5-1.5B (online round-to-nearest): nothing to gain from a search over cheap candidates; what is left of the gap to fp16 is the 4-bit weights (GPTQ takes it from 13.4 to 12.3), not the basis. (2) FP8 (e4m3) activations instead of INT8 on the Ada tensor cores: not built. With the rotation the INT8 activations cost only +0.01 / +0.04 perplexity on top of the 4-bit weights (rotation_ppl.py, variants rot-w4 vs rot-w4a8), so there is no quality left to win, the FP8 and INT8 mma rates are the same on this chip, and LLVM 18's NVVM dialect has no FP8 mma (it would need inline PTX and a second fragment path in the compiler). (3) fp8 KV cache (QF_KV=fp8 in vllm_ppl.py / vllm_batch_sweep.py): it works with the W4A8 path and doubles the KV capacity (90,385 -> 170,670 tokens on the 6 GB card), but vLLM's default KV scale of 1.0 breaks Qwen2.5 (PPL 12.33 -> 24.96; the Marlin GPTQ checkpoint goes 13.64 -> 28.73 the same way), so it is not recommended without calibrated scales, which are vLLM's attention business and not something these GEMM kernels touch.
  • Negative result, W4A8 for mixture-of-experts: a grouped INT8 kernel (W4A8GemmDq through ExpertBatchPass, roles reeerer, OLMoE shapes, cold weights, 64 experts, best of the INT8 schedules of int8_plan) against the tuned grouped W4A16 kernel: 256 tokens (32-row tiles) gate/up 875 us vs 925 us, down 474 vs 504 us (5-6 %: both near the 192 GB/s of the memory), 512 tokens (64-row tiles) 1223 vs 1451 us and 682 vs 790 us (14-15 %). The INT8 path needs a quantisation kernel before each grouped GEMM and an f16 gate/up buffer plus a swiglu + requantisation kernel between them (about 0.15-0.2 ms of memory traffic per layer at 512 tokens), which eats most of the 0.34 ms kernel gain: prefill would go from 0.88x to roughly 0.92x of Marlin MoE, not past it, for a new online-quantisation loader in vLLM. Not built.
  • Clipping (research/rotation_ppl.py --clip, --chclip; quant.w4a8_quantize(..., channel_clips=...), default off): with float group scales a per-group search of the clip ratio (1.0 .. 0.6) takes the rotated W4A8 of Qwen2.5-1.5B from 13.606 to 13.085 (0.5B 21.337 -> 20.95) and does almost nothing without the rotation (13.512 -> 13.484): the rotated weights are close to Gaussian, whose best 4-bit range is narrower than min-max. The real W4A8 format already minimises each group's squared error over its integer scale 1..16 and zero point (an implicit clip), so only the per-channel INT8 scale is left to search: ratios 1.0 .. 0.7 of the channel maximum change the fake-quantised perplexity by -0.08 (1.5B, 13.388 -> 13.305), +0.08 (0.5B, 21.190 -> 21.269) and -0.26 (OLMo-2 1B, 18.964 -> 18.703): not consistent, so the default stays 1.0. The remaining 0.2-0.3 between the float-scale simulation and the real format is the coarse integer group scale, which would need a different kernel format (e.g. group 64 or a 2-level scale), not a better search.
  • Group size of the W4A8 format, now wired in for 64 (quantforge_w4a8_g64, make_w4a8_checkpoint.py --group 64, W4A8Linear.group inferred from the scale shape, group argument of the kernel builders and of the op, checkpoint group_size; the two-layouts mode keeps 128): vLLM perplexity of Qwen2.5-1.5B online 13.395 -> 13.186, GPTQ checkpoint 12.331 -> 12.253; 1.5-2.5 % slower. Measurements that led to it: the integer group scale 1..16 is the coarse part of the format. Rotated online W4A8 of Qwen2.5-1.5B (real quantiser, fake-quantised perplexity): group 128 13.388, 64 13.170 (-0.22), 32 12.907 (-0.48). The compiled INT8 kernel builds and is exact for groups 64 and 32 with e2e.W4A8_GROUP changed (relative error 0.0002): 4096 x 4096 at 64 / 128 / 256 rows 63.5 / 98.3 / 177.2 us (128) against 64.5 / 103.4 / 178.2 (64) and 72.7 / 111.4 / 184.3 (32); 1536 x 17920 +3 / +2 / +2 % for group 64 and +10 / +6.5 / +4 % for group 32. The scale and zero point bytes double / quadruple (1.6 % / 3.1 % / 6.3 % of the weight bytes for 128 / 64 / 32 ... on top of the 0.5 byte of the nibbles). Using it means carrying the group size through the op signature, the compact decode kernel, the pack keys, the planners and W4A8Linear (the tile K is 128 there); the quality gain is already beyond Marlin's GPTQ, so 128 stays the default.
  • Fewer bits (research/gptq_bits.py: sequential GPTQ, float group scales of 128, INT8 activations, 64 calibration windows of wikitext-2 train, Qwen2.5-1.5B, wikitext-2 test perplexity; fp16 11.932): 4 bit 13.125 -> 12.478 with the rotation -> 12.363 with the rotation and GPTQ's clip search; 3 bit 17.223 -> 14.629 with the rotation -> 13.586 with the rotation and the clip search; RTN 3 bit 32.7 -> 23.3 -> 19.0 and 2 bit is unusable (3404 at best). So rotation + clip makes 3-bit weights as good as the public Marlin 4-bit GPTQ (13.636, other calibration data), but against 4-bit GPTQ with the SAME calibration it costs +0.5 to +1.2 perplexity for 25 % fewer weight bytes (at most 1.33x on the memory-bound decode). Not built: the generated kernels have no 3-bit unpack, the only way without a new compiler op is two bit planes read by tensor.extract producers like the W4A8 decode kernel, which already runs 1.1-1.7x slower than the dedicated 4-bit decode kernel, so the byte saving would not become speed.
  • Rotation on other models: it is not a free win. Llama-3.2-3B online got WORSE (16.640 -> 17.752) because of one layer (layers.1.mlp.down_proj: massive-activation token, 530x the median norm; rotated alone 17.71, everything else rotated 16.74); found by rotating by input size, then by a per-layer error table on real activations (down_proj plain 0.054, rotated 0.080). Fixes: the online method leaves the down_proj of decoder layers 0-3 unrotated (_early_down_proj; six models: Qwen 1.5B 13.395 -> 13.376, Qwen 0.5B 21.195 -> 21.395, OLMo-2 18.953 -> 18.987, Phi-3.5 9.007 -> 8.718, Llama-1B 22.257 -> 21.539, Llama-3B 17.752 -> 16.658), and GPTQ decides per layer (gptq._rotation_helps, unrotated_layers in the checkpoint config, honoured by the plugin through the layer prefix; groups that share an input decide together). Llama-3.2-3B GPTQ W4A8: 16.537 plain, 16.377 with the decision. Also a lesson in method: the first bisection edited the wrong layer.qf_rot line (the checkpoint branch) and both runs repeated the all-rotated result; the numbers only moved when the right line was changed.
  • W4A8 rotation: block-Hadamard (128) rotation of weights and activations. quantization="quantforge_w4a8" (online) rotates by default (quantforge_w4a8_plain = the old method); benchmarks/make_w4a8_checkpoint.py --rotate runs GPTQ in the rotated basis (gptq.rotate_hessian) and marks the checkpoint "rotated": true. Wikitext-2 PPL in vLLM, Qwen2.5-1.5B: online 13.949 -> 13.395, GPTQ 12.864 -> 12.331 (fp16 11.932, GPTQ W4A16 12.605); 0.5B online 23.148 -> 21.195. New CUDA kernels hadamard128 and quantize_rows_rot (act_quant.cu), op flag w4a8_hybrid(..., rotate), W4A8Linear.rotate. Throughput against Marlin (1.5B, GPTQ checkpoint): 0.92 / 0.93 / 0.97 / 0.98 / 1.01 / 1.11 / 1.16 at 1 / 16 / 32 / 64 / 128 / 192 / 256 requests (unrotated: 0.95 ... 1.18). Found while testing it: vLLM's compile cache is keyed by the quantisation name, not by environment variables, so an env switch that changes the traced graph silently reuses the other graph (wrong results, PPL 1e7); a custom op's fake must return the real output's strides (empty_like of a non-contiguous input does not).\n* W4A16 op: the activation rows of 65..256-row calls are padded with one CUDA kernel (pad_rows_cuda, act_quant.cu) instead of constant_pad_nd (3 small launches); no measurable change in the GEMM times (within noise). Negative results recorded while looking for the 0.74-0.80x of the exact W4A16 path at 96-256 rows: independent of the KV-cache fraction, not a wave-quantisation effect (split-K at 128 rows: 165 us vs 155 us), both kernels latency-bound (ncu: Marlin 115 us at 50 % DRAM, ours 154 us at 36 %); what is left is a weight format whose B fragments go from global memory straight to registers.
  • MoE decode in vLLM, re-measured after the f16 swiglu output (four interleaved rounds at 16 and 32 requests): 0.96 / 0.95 / 0.95 / 0.93x of Marlin MoE at 1 / 8 / 16 / 32 requests. The "0.66x at 32 requests" of the first version was a KV-cache artifact (its f32 intermediate buffer shrank the KV cache and vLLM preempted), and the long search for a kernel-level cause of that gap (nsys, ncu, micro-benchmarks, real-routing replay) was chasing it.
  • MoE prefill: 0.58x -> 0.88x of vLLM's Marlin MoE (OLMoE-1B-7B, 16 x 1275-token prompts: 6873 -> 10616 tokens/s; decode unchanged at ~0.93-0.97x). (1) quantforge.swiglu_out: the swiglu epilogue can store silu(gate) * up into its own f16 [M, N/2] argument (FuseEpiloguePass; GroupedGemm(kind="swiglu16")), so the f32 gate/up buffer and the cast kernel are gone and the token chunks grow from 256 to 512 (every chunk reads all the experts again). (2) Own schedules for the grouped 32 / 64 / 128-row kernels (moe._opts): the dense rule used block-m 64 inside 128-row problems (weights read twice) and the wrong warp tiles; sweeps with the read-only flush found K tile 64, one stage, look-ahead 1, 128-column blocks, 17-27 % faster (gate/up 1414 -> 1029 us at 256 tokens with a 64-row tile). (3) Row tile 16 / 32 / 64 by rows per expert (128 rows never won). Found by measuring the regime that had never been measured: MoE prefill.\n* W4A8 op: the per-token INT8 quantisation of the activations is one CUDA kernel of the C++ runtime (runtime/act_quant.cu, op quantize_rows) that also writes the zero rows up to the bucket, instead of a torch.compiled function (Triton / inductor needed at run time, compiled by the first big call) plus two padding copies when the row count is not a bucket. Bit-identical to the eager torch expression (the compiled one multiplies by a reciprocal and differs on exact .5 ties). 5-10 us per call at 20-100 rows: 20 x 8960 x 1536 60.4 -> 50.2 us (0.80 -> 0.96 of Marlin), 64 x 8960 x 1536 0.95 -> 1.07, 20 x 4096 x 4096 0.90 -> 1.00, 40 rows 0.83 -> 0.92. QUANTFORGE_NO_NATIVE_QUANT=1 restores the old path. In vLLM (Qwen2.5-1.5B, two interleaved rounds against Marlin) the W4A8 path is now 0.95 / 0.96 / 0.99 / 0.99 / 1.04 / 1.13 / 1.18x at 1 / 16 / 32 / 64 / 128 / 192 / 256 requests.
  • scripts/memcheck_ops.py: the production ops (W4A16 with the atomic split-K, K-fold and f16-store paths, W4A8 compact, MoE) over 15 row counts x 4 layer shapes of Qwen2.5-0.5B under compute-sanitizer --tool memcheck with the caching allocator off: 0 errors. (It is the check that found the 2-byte-vs-4-byte scale read of the INT8 planner inside vLLM.)
  • benchmarks/vllm_ppl.py: perplexity of any model through vLLM (prompt log-probabilities of wikitext-2 windows). Qwen2.5-1.5B-Instruct: fp16 11.932, GPTQ-Int4 via Marlin 13.636, via quantforge 13.637, online W4A8 13.991. With this repository's GPTQ and the same calibration (wikitext-2 train, in-domain for the test split): W4A16 via quantforge 12.605, W4A8 checkpoint 12.851, i.e. +0.25 perplexity for the INT8 activations and integer group scales (Marlin cannot load the asymmetric W4A16 checkpoint). Tried and dropped: a K-major layout of the scales for the W4A8 decode kernel (no change in 60 us at 16 x 4096 x 4096; the kernel reads 77 % of the DRAM peak against 89 % for the W4A16 decode kernel with 14 % more instructions because its layout puts the nibbles of 8 rows in 8 different 4-byte loads: fixing it means storing the weights in the W4A16 layout and teaching the INT8 kernel to read it, a bigger change for 3-5 % end to end at 1-16 requests).
  • Re-measured in vLLM (Qwen2.5-1.5B, two interleaved rounds) the exact W4A16 path against Marlin: 0.94 / 0.94 / 0.89 / 0.84 / 0.80 / 0.86 / 0.85 at 1 / 16 / 32 / 64 / 128 / 192 / 256 requests (the README had 0.93 / 0.93 / 0.91 / 0.85 / 0.81 / 0.88 / 0.87, measured several sessions earlier).
  • W4A8 faster than Marlin from 64 rows of GEMM (int8_plan.py, W4A8GemmDq(kmajor=True), quant.kmajor_scales, benchmarks/compare_marlin_ops.py). ncu on the INT8 kernel at 64 rows x 4096 x 4096: 67 % of the stall cycles are long-scoreboard (waiting on global loads); the rule of w4a8_op had been tuned on narrow layers (N <= 2048) and picked a 64 x 128 block with a 128-deep K tile for the square layers: 115 us. A sweep of 64 / 128 / 256-row blocks, 32 / 64 / 128 columns, K tiles 64 / 128 / 256, 2-8 warps, 1-3 stages and look-ahead 0-2 on eight shapes found 64 x 64 blocks with a 256-deep K tile and 16 x 32 warp tiles at 65 us (Marlin 61-67), 253 -> 145 us at 64 x 4096 x 11008, 65 -> 54 at 32 rows, 112 -> 103 at 128 rows, 183 -> 175 at 256. Because the best schedule depends on the shape it is measured once per (GPU, rows, K, N) like the W4A16 tile planner (int8_plan.plan_int8, 4 % margin, decisions in the autotune cache and in kernel packs, pack.sweep_w4a8 and the plugin call preplan; QUANTFORGE_NO_TILE_PLAN=1 disables). The integer group scales / zero points are also kept as int8 [K/128, N] (a second 3 % copy in the slots the compact layout leaves empty; with ONE extra zero row, because the look-ahead of the last K tile reads the next group's row): the 8 output channels of a thread are then adjacent bytes, 5 % faster. Op level against Marlin on 4096 x 4096: 0.95 / 1.02 / 1.06 / 1.15 / 1.17 / 1.22 at 32 / 64 / 96 / 128 / 192 / 256 rows (was 0.80 / 0.68 / 0.53 / 1.03 / - / 1.15); in vLLM (Qwen2.5-1.5B, two interleaved rounds) 0.94 / 0.96 / 0.97 / 0.98 / 1.01 / 1.08 / 1.13x of Marlin at 1 / 16 / 32 / 64 / 128 / 192 / 256 requests (was 0.95 / 0.96 / 0.95 / 0.97 / 0.96 / 1.06 / 1.06). The W4A16 op (exact Marlin numerics) is unchanged: 1.00 at 1-16 rows, 0.75-0.94 above.
  • Lessons that cost time here: (1) a benchmark that flushes the L2 by writing (zero_()) leaves dirty lines whose write-back slows the next kernel: it showed the same rule at 147 us instead of 115 us and hid the real gap; flush by reading (.max()), as autotune.event_time does. (2) vLLM sets torch's default dtype to the model's while loading, so a planner's torch.rand(...) without dtype= made f16 scale tensors for a kernel that reads f32: out-of-bounds reads only inside vLLM (found with compute-sanitizer on the engine load: 0 errors afterwards). (3) nsys needs --cuda-graph-trace=node to see the kernels inside CUDA graphs.
  • Prefill: the C++ op split long inputs into chunks of 2048 rows and copied every chunk's f16 result into the output (73 MB per chunk for N = 17920): 202 ms of Memcpy DtoD in a 16 x 1000-token prefill of Qwen2.5-1.5B (12 % of the GPU time). Exact chunks now write straight into their slice of the output (33 ms of copies left, the padded tail chunk): vLLM prefill 9380 -> 10289 tokens/s. Correction: the README claimed W4A16 prefill 1.1-1.15x of Marlin; measured in vLLM now it is 0.90-0.92x (GEMM time 1162 ms against 1050, and 0.9-1.04x per op at 384-2048 rows); W4A8 prefill is 1.07-1.14x. Found by comparing kernel-time profiles of the two prefill runs.
  • Mixture-of-experts (quantforge.moe, lib/Transforms/ExpertBatchPass.cpp, runtime/moe_kernels.cu, QuantForgeMoEMethod): two compiler passes (quantforge-expert-batch-launch, quantforge-expert-batch-pointers; pipeline options expert-problems, expert-roles) turn any dense kernel into a grouped one (grid.z row-block problems, expert read from an int32 array, per-expert weight pointers, padding problems return at once; lit test gpu_pipeline_expert_batch.mlir). moe.moe_ffn_impl = routing / gather / cast / combine CUDA kernels + grouped swiglu GEMM + grouped down GEMM, no host synchronisation (CUDA graphs capture it), tokens beyond 256 run in chunks (bounded f32 buffer: a first version with 1024-token chunks cost vLLM a third of its KV cache and was measured as 0.28x of Marlin at 32 requests for that reason alone). vLLM plugin: GPTQ / AWQ MoE layers (vLLM 0.25.1 and 0.34.0) reuse vLLM's loader and router. OLMoE-1B-7B GPTQ: identical text to vLLM's Marlin MoE, 0.94x of its decode speed at 1-16 requests, 0.66x at 32. pack build / check record and verify the grouped kernels (pack.moe_dims, pack.sweep_moe). A sweep of the grouped decode schedule (block-tile-n 32..256, warp tile, K tile 32..256, 1..3 stages, look-ahead 0..2, smem pad, sink-dequant-stores, vectorize-dequant) found a 128-column block with one stage and a look-ahead of one tile 12-16 % ahead of the dense decode rule and then a plateau at 148 GB/s (torch's sum reads 164 GB/s of the same memory): the kernel is within 10 % of what the memory gives, the rest against Marlin is overlap at many experts.
  • Extension tags by torch major.minor (torch2.14-cu13.0-abi1-py312; torch patch releases share an ABI; 0.4.0 exact-version directories are still found), quantforge-pack ext --cuda-home (default: the installed toolkit matching the torch's CUDA), quantforge-pack install --build-ext and a message that says which runtime the pack lacks, scripts/build_ext_matrix.sh (throwaway uv venvs, torch 2.8-2.15 x Python 3.10-3.13). Verified: a pack built under torch 2.11 runs under torch 2.15 after pack ext (errors <= 6e-4 against the dense reference), and without any matching extension and without nvcc the op falls back to its Python path with correct results.
  • e2e.w4a16_f16_ir (the f16-store IR as a function).

0.4.0 - 2026-11-22#

First release prepared for PyPI under the distribution name quantforge-llm (the name quantforge belongs to an unrelated project; the import name stays quantforge).

  • quantforge.gptq_checkpoint.save_gptq + benchmarks/make_gptq_checkpoint.py + benchmarks/vllm_check_gptq_checkpoint.py: quantise any Hugging Face causal LM with the repository's GPTQ and write a standard GPTQ checkpoint that vLLM loads. Llama-3.2-1B-Instruct (a family other than Qwen: GQA, tied head, no bias) in vLLM with the QuantForge kernels gives the same 289 greedy tokens as Hugging Face with the same weights, log-probability difference 0.001-0.003; from a pack alone 151 / 583 / 2119 / 5419 / 6791 / 7375 tokens/s at 1 / 4 / 16 / 64 / 128 / 256 requests (W4A8 online: 151 / 581 / 2137 / 5427 / 7565 / 8995). vLLM's Marlin refuses the checkpoint (it only loads symmetric GPTQ; this one keeps the zero points).
  • W4A8 single-layout (compact) is now the default (QUANTFORGE_W4A8_DECODE=w4a16 restores the two layouts): its decode kernel got a tile schedule for the single layout (w4a8_op._decode_opts: 256-deep K tile, 8-wide warp tiles, 32-/64-column blocks; cold weights, us, old -> new: 4096 x 4096 89.8 -> 57.5, 8960 x 1536 83.2 -> 51.8, 11008 x 2048 109.5 -> 76.7, 1536 x 1536 13.0 -> 10.3, 1536 x 17920 82.8 -> 80.0) and the 32- / 64-row INT8 kernel a better one (_int8_opts: 64-column blocks, 16 x 32 warp tiles, 256-deep K tile; 8960 x 1536 93 -> 54 us at 32 rows, 94 -> 60 at 64, 1536 x 1536 16.6 -> 11.5). vLLM, Qwen2.5-1.5B online W4A8, one weight copy (1.13 GiB, the two layouts took 2.04) / Marlin, two interleaved runs, at 1 / 16 / 32 / 64 / 96 / 128 requests: 0.95 / 0.96 / 0.95 / 0.97 / 0.95 / 0.96 (it was 0.78 / 0.79 / 0.77 / 0.84 / 0.91 / 0.95) and still 1.06 at 192-256.
  • W4A8 kernels in packs: pack build --w4a8 / pack check --w4a8 (pack.sweep_w4a8), and w4a8_op falls back (the W4A16 kernels for the dual layout, a dense matmul with the dequantised weight for the compact one; w4a8_op.FALLBACKS, one warning) when a W4A8 kernel is in no pack and cannot be compiled, instead of raising. Nine-model pack with W4A8: 1566 kernels, 94 MiB, built in 191 s; from it alone Qwen2.5-1.5B W4A8 / Marlin at 1 / 16 / 64 / 128 / 192 / 256 requests 0.93 / 0.94 / 0.86 / 0.95 / 1.06 / 1.06 (QF_GPU_UTIL=0.7).
  • W4A8 INT8 kernel for 96..256 rows (w4a8_op._int8_opts, buckets 96 / 128 / 160 / 192 / 224 / 256 instead of 128 / 256): the 128 x 128 block with 64 x 64 warp tiles of the large-batch schedule is a poor fit below ~512 rows; with 32 x 128 or 64 x 64 blocks (cold weights, us, default -> new) 8960 x 1536 at 128 rows 183 -> 108 and at 256 rows 186 -> 139, 1536 x 17920 at 128 rows 165 -> 138, at 256 rows 266 -> 243; the INT8 path now beats the W4A16 kernels at nearly every row count from 96 up (1536 x 17920 at 192 rows 207 against 314 us). vLLM, Qwen2.5-1.5B online W4A8 / Marlin (GPTQ) at 64 / 96 / 128 / 192 / 256 requests: 0.64 (before the 64-row threshold) -> 0.86 / 0.83 -> 0.94 / 0.89 -> 0.95 / 0.72 -> 0.82 / 0.73 -> 0.77 (5036 / 5934 / 6943 / 6372 / 6110 against 5877 / 6330 / 7302 / 7734 / 7903 tokens/s). Those 192 / 256-request figures (0.82 / 0.77) were an artefact of the benchmark's memory budget, not of compute: vllm_batch_sweep.py fixes gpu_memory_utilization = 0.55 of a 6 GB card, the two-layout W4A8 weights (2.0 GiB, against 1.0 for W4A16) leave too little KV cache for 256 sequences, so vLLM ran them in two waves (1.5x the decode steps in the profile: 5320 flash-attention launches against 3584). With QF_GPU_UTIL=0.7 (a new environment variable of the script; 0.8 runs out of memory on this card for the QuantForge plugin), same session, two runs: Marlin 5642 / 7074 / 7480 / 7663 tokens/s at 64 / 128 / 192 / 256 requests, QuantForge W4A16 4823 / 5666 / 6470 / 6564, W4A8 4890 / 6727 / 7963 / 8175: 1.06-1.07x of Marlin at 192-256 requests, 0.95 at 128, 0.87 at 64. (W4A8 is not the same numerics as Marlin's W4A16: INT8 activations, and round-to-nearest quantisation when the checkpoint is quantised on load: wikitext-2 perplexity of the 0.5B 23.7 against 20.5 for GPTQ W4A16, 21.1 with a GPTQ-quantised W4A8 checkpoint.) QUANTFORGE_W4A8_DECODE=compact (one copy of the nibbles, 1.13 GiB instead of 2.04 on the 1.5B) gives the same at 192 / 256 requests with the default 0.55 budget (7940 / 8150) and, with INT8 buckets of 32 and 64 rows added for it (17-95 rows were padded to 96), 2834 / 4909 / 5753 tokens/s at 32 / 64 / 96 requests; its decode at 1 / 16 requests is 0.78 / 0.79 of Marlin.
  • 65..256 rows (decode at 65-256 concurrent requests): the row buckets are multiples of 32 there (96, 128, 160, 192, 224, 256; was 128, 256) with 32- or 64-row blocks (torch_ops._mid_opts, refined per shape by tile_plan.plan_tile when a pack is built, QUANTFORGE_PLAN_MID=1). A batch of 96 rows was padded to 128 and one of 192 to 256, 25-33 % of the arithmetic of a compute-bound GEMM thrown away, and the 128-row tile is a poor fit for the skinny sizes: kernel level, cold weights, 8960 x 1536 at 96 rows 263 -> 119 us, 4096 x 4096 150 -> 108, 1536 x 2048 54 -> 29, 1536 x 17920 244 -> 209; the very wide outputs (N >= 20000) keep the 128-row tile. vLLM, 1.5B, QuantForge W4A16 / Marlin at 96 / 128 / 192 / 256 requests: 0.63 / 0.69 / 0.70 / 0.85 -> 0.84 / 0.81 / 0.88 / 0.87; 3B 0.79 / 0.82 / 0.79 / 0.76 (average of two interleaved runs from a nine-model pack; the laptop throttled between sessions, ratios inside a session are what counts). The W4A8 hybrid op used the INT8 kernel from 17 rows on, where it has a ~170 us floor (1536 x 17920 at any M <= 128): its threshold is now 64 rows (QUANTFORGE_W4A8_MIN_ROWS; 32 requests 2054 -> 3361 tokens/s, 64 requests 3756 -> 5019); the W4A16 / INT8 crossover is shape dependent (INT8 wins from 96 rows for 1536 x 17920 and 2048 x 22016, from 224 for 8960 x 1536 and 4096 x 4096), a per-shape route would gain a few % more.
  • Per-shape tile schedule for 16 rows too (tile_plan.plan_tile(16, K, N), N > 2048): the decode rule takes a 64-deep K tile below N = 8192, which the cp.async copy of the 16 x bk activation tile cannot split evenly over the threads, so the exact-row kernels of M in {1, 2, 4, 8} (valid-rows) could not be built there and the op copied the activations to a padded buffer first (one more kernel). The planner times each schedule on the path the op takes for one row (padded copy included) and keeps one that wins by 3 %.
