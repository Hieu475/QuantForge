End-to-end on a real model#

benchmarks/qwen_end_to_end.py and benchmarks/qwen_decode_graph.py run Qwen2.5-0.5B-Instruct with its official GPTQ-Int4 checkpoint, every decoder Linear replaced by the QuantForge kernel (the gate_proj + up_proj fused into one GEMM with the swiglu epilogue, q/k/v_proj fused into one GEMM with quant.concat_columns), on the RTX 4050 laptop GPU:

wikitext-2 test, 8 × 512 tokens perplexity
fp16 original 19.93
GPTQ weights dequantised to dense fp16 (reference) 23.195
QuantForge 23.194
QuantForge + lm_head RTN 4-bit (--quant-head, not in the checkpoint) 25.36

The QuantForge model reproduces the dequantised reference (logit |Δ|max 0.10 on a logit std of 2.9, top-1 agreement 99.2 %, the fused gate/up keeps silu * up in f32 where the reference rounds to f16 in between; 48 of 48 greedy tokens identical). Batch-1 decode, whole step captured in a CUDA graph (static KV cache):

tokens/s
fp16 129
QuantForge (GPTQ checkpoint) 196 (176 with q/k/v as three GEMMs)
QuantForge + RTN 4-bit lm_head 239 (perplexity +2.2: not recommended)

GPU time of one decode step before the q/k/v and gate/up fusions: the 168 W4A16 kernels took 2.6 ms against 4.4 ms for the same layers in cuBLAS fp16 (now 120 kernels); what stays is the fp16 lm_head (272 MB, ~1.7 ms), attention / norms (~1.3 ms) and the small kernels around each call (activation padding, f32 → f16). Without the graph (HF generate, Python launching every kernel) the per-call overhead decides: the Python op gives 54 tokens/s, the C++ dispatcher hot path (see "As a PyTorch op") ~79 (71 before the fused gate/up, q/k/v and the overwrite kernel removed launches), fp16 ~100 — the layers of a 0.5 B model are only 10–15 µs of GPU time each and every call still launches four small kernels around the GEMM (activation pad, f32 → f16 conversion, plus the GEMM; the accumulator zero-init is gone since kernels can overwrite their output).

Inside vLLM (plugin)#

pip install -e ./python --no-deps       # registers the plugin through the `vllm.general_plugins` entry point
export QUANTFORGE_BUILD_DIR=$PWD/build
python -c "from vllm import LLM; LLM('Qwen/Qwen2.5-0.5B-Instruct-GPTQ-Int4', quantization='quantforge', dtype='float16')"

quantization="quantforge" loads a 4-bit GPTQ checkpoint exactly as vLLM does (tensor parallelism, fused qkv / gate_up layers, desc_act) and converts it once into the QuantForge layout; every linear layer then runs torch.ops.quantforge.w4a16_gemm (works under vLLM's torch.compile and CUDA graphs). Output agrees with Marlin (benchmarks/vllm_compare_outputs.py: 4 of 5 prompts identical over 64 greedy tokens, the fifth for 34 tokens; mean |log-probability difference| 0.002, max 0.017). The kernel-level table (M = 1, K x N) showed where the rest went: qkv 1536 x 2048 0.94x, gate/up 1536 x 17920 0.93x, but o_proj 1536 x 1536 0.73x, down_proj 8960 x 1536 0.62x and 4864 x 896 0.55x: a long K with a narrow N gives only 12-24 blocks for 20 SMs. No tile / prefetch option fixes it (swept), so the plugin folds K (python/quantforge/kfold.py, QUANTFORGE_KFOLD=0 to disable): K is cut into S slices that are laid side by side as columns of one wider GEMM (and as S rows of the activation). The tensor-core tile already has 16 rows, so while M * S <= 16 the S-fold redundant arithmetic is free, the weights are still read once, by S times as many blocks with a K loop S times shorter. No compiler change; costs a second copy of the weights of the folded layers (only layers with N <= 2048). Kernel level, M = 1 (us, whole op in a CUDA graph): 4864 x 896 37.7 -> 23.3, 8960 x 1536 68.5 -> 43.0, 1536 x 1536 14.4 -> 12.6. Prefill through the plugin 20.6k -> 28.0k tokens/s (no f32 buffer; Marlin 33.7k).

Split-K with an in-kernel reduction (epilogue=atomic-add, a later session). The narrow, long-K layers (down_proj: 8960 x 1536 on the 1.5B, 4864 x 896 on the 0.5B) only had K-folding, which serves 16 // S rows, so from 4 requests up they ran the plain kernel at 0.6-0.8 of Marlin (8960 x 1536 at 16 rows: 60 us against 41). The K reduction is now cut over S blocks that add their partial results with red.global.add.f32 to a zeroed f32 buffer (quantforge-fuse-epilogue; the partial buffer and the reduce kernel of the old experimental split-k are gone, so there is no per-call allocation and the call is CUDA-graph safe), and the op converts it to f16 + bias with one more kernel; no second copy of the weights, any 1..16 rows. A planner (atomic_plan.py, measured once per GPU and shape) turns it on only where it is at least 12 % faster: 8960 x 1536 60 -> 46 us, 4864 x 896 26.7 -> 24.3 us; 1536 x 1536 and 896 x 896 keep the plain kernel. vLLM decode, QuantForge / Marlin at 1 / 4 / 16 / 64 requests (two interleaved runs each): 1.5B 0.92 / 0.92 / 0.92 / 0.81 (was 0.91 / 0.88 / 0.86 / 0.81; 129 / 509 / 1924 / 4783 tokens/s against Marlin 142 / 554 / 2091 / 5893), 0.5B 0.96 / 0.96 / 0.93 / 0.88 (was 0.95 / 0.95 / 0.92 / 0.88; 297 / 1133 / 4082 / 10387 against 308 / 1181 / 4368 / 11721). The summation order of the atomic adds varies, so two runs differ by an ulp in the layer outputs; QUANTFORGE_NO_ATOMIC=1 restores the deterministic path. What is left at the kernel level is the gate / up layer (0.89-0.90, 79 % of the DRAM bandwidth) and the 64-row kernels (0.67 at 4096 x 4096): a hand-written CUDA prototype with Marlin's register-resident B layout (benchmarks/proto/bir_w4a16.cu, 16 rows) reached 52.2 us at 4096 x 4096 (compiler 50, Marlin 49.6) and 178 / 155 us at 4096 x 11008 (compiler 135.7, Marlin ~126), so repacking the weights is not what separates them from Marlin.

Fold helps for 1-4 requests (+9 % / +15 % at the time, about +4 % now that the plain schedules are better) and does nothing from 16 requests up (more than 16 // S rows: the plain kernel runs). The last two columns add, first, the width-aware default schedules (the tile options of the 17 to 64-row kernels and of the narrow-output decode kernels were tuned on 4096 x 4096 and were 1.5 to 3 times too slow for the small shapes of these models; autotune picks 32 / 64-column blocks and a look-ahead there, and I turned its winners into rules, benchmarks/sweep_skinny.py), then a second sweep that found 32 and 64-column blocks 11 to 52 % faster than 128-column ones for N <= 2048 at 32 and 64 rows (for wide outputs no candidate of 74 beat the defaults by more than 4 %, benchmarks/sweep_skinny_blocks.py) and a fused epilogue kernel for the folded layers (3 kernels per call instead of 5 to 7: 20 to 35 % faster per layer, but invisible in whole-model time, about 1 to 2 %, because the GPU is busy 97 % of the time anyway). Together: the 0.5B model reaches 0.87 to 0.96 of Marlin at 1 to 64 requests, the 1.5B model 0.74 to 0.87; the absolute speed rose by 4 to 7 % over the previous column. Ratios come from one run of Marlin and QuantForge back to back; Marlin itself moves by about 4 % between runs with the laptop's clocks.

Split-K in the compiler (experimental, off by default). The ncu comparison at 64 rows shows Marlin running 20 persistent blocks (one per SM, tensor pipe 67-75 % busy) where this compiler launches 32-76 blocks (50 %). --quantforge-gpu-pipeline='... split-k=S' cuts the K reduction into S grid chunks (linalg::tileReductionUsingForall, merged into one 3-D scf.forall, partial results [S, M, N] plus a reduce kernel). It is correct (relative error 2e-4, test/Transforms/gpu_pipeline_split_k.mlir, test/E2E/test_split_k.py) but not worth enabling: 14-23 % faster on long-K, narrow-N layers at 32 rows (8960 x 1536: 86.5 -> 66.2 us), slower at 64 rows for most shapes (4096 x 4096: 94 -> 114 us) and behind K-folding at 16 rows, because of the second kernel, the extra partial-result traffic and a per-call buffer (which would break CUDA graphs). Details and the full table in the blog post.

Pitfall found on the way: vLLM caches its compiled graphs (~/.cache/vllm/torch_compile_cache) by a hash that does not see the plugin, so a graph compiled before a plugin change is silently reused (my first A/B measured nothing for that reason). The plugin therefore makes every layer call the same op and derives the fold factor from tensor shapes at run time; after upgrading the plugin, clear that cache once.

vLLM versions: needs >= 0.24 (the classes it extends do not exist before); the generation tests (GPTQ 4-bit, GPTQ 8-bit, AWQ against the matching Marlin method) pass on 0.24.0, 0.25.1 and 0.34.0, the releases in between were not run. Two API changes had to be absorbed on the way (0.34 reads use_batch_invariant in create_weights; is_layer_skipped changed its keyword), which shows that a new vLLM release may need a small fix. Formats: GPTQ 4-bit and 8-bit (symmetric or not, act-order included) and AWQ 4-bit with zero points (quantization="quantforge" picks the reader from the checkpoint). Limitations: no MoE layers, no AWQ without zero points. Mixture-of-experts models (quantization="quantforge")#

A MoE layer is many small GEMMs with the same shape and different weights. The compiler gets one more feature for it (ExpertBatchPass.cpp, pipeline options expert-problems / expert-roles): the ordinary dense kernel is launched with grid.z = a list of row-block problems, takes the expert of each from a device int32 array (meta[z]; a negative entry is padding and the block returns at once) and advances its weight / scale / zero-point pointers by that expert's slab, its activation / output pointers by the problem's slab. Rows are sorted by expert and padded to the row tile, so every row block belongs to one expert; everything has static shapes and no host synchronisation (CUDA graphs capture it). quantforge.moe wraps it: three small CUDA kernels (runtime/moe_kernels.cu: routing, gather, combine) around two grouped GEMMs (gate/up with the fused SwiGLU epilogue, then down); QuantForgeMoEMethod in the vLLM plugin takes vLLM's own MoE weight loader and router and replaces only the expert computation (vLLM 0.25.1 and 0.34.0, 4-bit GPTQ / AWQ, silu-gated experts, no expert parallelism).

Measured on OLMoE-1B-7B GPTQ (64 experts, top-8, 3.7 GiB; the checkpoint quantises the router too, which vLLM cannot load, so the router was dequantised to fp16 in a local copy used by both sides), RTX 4050 laptop, vLLM 0.34, CUDA graphs, pure decode step time with the KV cache not limiting:

concurrent requests 1 8 16 32
Marlin MoE (vLLM), tokens/s 197 814 1556 2536
QuantForge, tokens/s 189 771 1475 2354
ratio 0.96 0.95 0.95 0.93

(mean of four interleaved rounds for 16 and 32 requests, two for 1 and 8). An earlier version of this section said 0.66x at 32 requests: that run had a smaller KV cache (the f32 gate/up buffer of this op, which no longer exists, took memory from it) and vLLM preempted; with the buffer gone the same measurement gives 0.93x.

Prefill (16 prompts of ~1275 tokens, 1024-token steps; vLLM's Marlin MoE 12117 / 11809 tokens/s): this op ran at 6873 / 6944 (0.58x), now 10616 / 10518 (0.88x). What changed it: the gate/up kernel writes silu(gate) * up as f16 itself (quantforge.swiglu_out, GroupedGemm(kind="swiglu16"): no f32 buffer, no conversion kernel, so the chunks could grow from 256 to 512 tokens and every expert's weights are read half as often), and the grouped kernels got their own schedules for 32 / 64-row tiles (a sweep over 64-256-column blocks, warp tiles, K tiles, stages: K tile 64, one stage, look-ahead 1, 128-column blocks, 17-27 % faster than the dense schedule of the same row count, which also read the weights twice per 128-row problem); the row tile is 16 / 32 / 64 by rows per expert (128 never won).

The generated text is identical to the one of vLLM's Marlin MoE on four prompts (40 tokens each; first-token log-probabilities within 0.001). Real decode routing is clustered (14.8 distinct experts per layer for 32 requests, 27 row blocks because experts with more than 16 tokens run as several blocks); the 16-row tile stays best there (32- / 64-row tiles measured slower). QUANTFORGE_MOE_ROWS forces the row tile for experiments. Only this one model was run end to end; pack build records the grouped kernels of any MoE config (Mixtral, Qwen-MoE, Qwen3-MoE shapes compile, they were not run). Shared experts (Qwen-MoE) go through the dense layers and were not tested.

Online W4A8 in vLLM (quantization="quantforge_w4a8", experimental)#

An ordinary fp16 / bf16 checkpoint (no GPTQ needed) is quantised to W4A8 (round-to-nearest, quant.w4a8_quantize, after the Hadamard rotation of "Hadamard rotation of W4A8"; quantforge_w4a8_plain skips it, quantforge_w4a8_g64 uses groups of 64) while vLLM loads it: LLM("Qwen/Qwen2.5-0.5B-Instruct", quantization="quantforge_w4a8", dtype="float16"). Every linear layer whose sizes are multiples of 128 calls torch.ops.quantforge.w4a8_hybrid (w4a8_op.py): above 16 rows the compiled W4A8 kernel on the INT8 tensor cores (the per-token activation quantisation is the compiled _int8_quantize_tokens; with an eager one the prefill was half as fast), up to 16 rows the W4A16 decode kernels (with K-folding), both from the same weight; the branch is inside the op, so torch.compile and CUDA graphs see none. Measured on vLLM 0.25.1 (RTX 4050; benchmarks/vllm_prefill.py: prefill of 16 prompts of 975 tokens, decode of 1 / 16 requests; tokens/s, best of 3):

High concurrency (a 6 GB card, vLLM, Qwen2.5-1.5B, QF_GPU_UTIL=0.7 of benchmarks/vllm_batch_sweep.py; two interleaved runs): the INT8 tensor cores pay off where the GEMMs are compute bound. Marlin 5642 / 7074 / 7480 / 7663 tokens/s at 64 / 128 / 192 / 256 requests; QuantForge W4A16 4823 / 5666 / 6470 / 6564 (0.85 / 0.80 / 0.87 / 0.86); QuantForge W4A8 4890 / 6727 / 7963 / 8175 (0.87 / 0.95 / 1.06 / 1.07), i.e. it is faster than Marlin from about 192 concurrent requests on, at the quality of W4A8 (INT8 activations; perplexity 23.7 round-to-nearest, 21.1 with the GPTQ-quantised W4A8 checkpoint, against 20.5 for GPTQ W4A16 on the 0.5B). Mind the KV cache: with the 0.55 memory budget of the sweep script the two-layout weights leave no room for 256 sequences and the run is slower for that reason alone.

Update: the one-copy layout (compact) is now the default and, with tuned decode and 32 / 64-row INT8 schedules, runs at 0.95 / 0.96 / 0.95 / 0.97 / 0.95 / 0.96 of Marlin at 1 / 16 / 32 / 64 / 96 / 128 requests and 1.06 at 192-256 (Qwen2.5-1.5B, two interleaved runs; weights 1.13 GiB instead of 2.04): the numbers of the table above and of the next paragraph describe the older two-layout default (QUANTFORGE_W4A8_DECODE=w4a16).

QUANTFORGE_W4A8_DECODE=compact keeps ONE copy of the nibbles: the decode reads the W4A8 layout itself (e2e.W4A8DecodeGemm, an f16 matmul_transpose_b with the weight tile built by a producer fused into the loads; benchmarks/w4a8_decode_layout.py: 1.0-1.75x slower than the dedicated W4A16 decode kernel) and the weights take 1.13 GiB instead of 2.04 GiB on the 1.5B; with the packed dequantisation pass below: prefill 36948 / 13273 / 6678 tokens/s (0.5B / 1.5B / 3B: 1.12x / 1.15x / 1.15x of Marlin), decode 269 / 3928 (0.5B), 115 / 1719 (1.5B), 69 / 1029 (3B) at 1 / 16 requests (after the f16-store epilogue and valid-rows also reached this kernel), i.e. 0.82-0.91x of Marlin. The fp16 weight of a layer that will be quantised is held on the CPU while the checkpoint is read (vLLM moves one module at a time to the GPU while it processes it), so the GPU never holds the whole fp16 model: Qwen2.5-3B (6 GB in fp16) runs on this 5.6 GB card in compact mode, 2.01 GiB of weights, prefill 6308 / decode 61 and 935 tokens/s at 1 / 16 requests, against 5782 / 81 / 1201 for GPTQ-Int4 with Marlin and 3923 / 71 / 1063 for the W4A16 plugin (QUANTFORGE_W4A8_LOAD_ON_CPU=0 restores the old behaviour; the two-layout mode needs ~3.9 GiB and does not fit).

So the prefill is at the level of fp16 / Marlin (1.05x on the 1.5B) and 1.6-1.7x the W4A16 plugin, the decode is the W4A16 kernels' (0.80-0.85x of Marlin). It is not a clear win over Marlin: its advantages are that it quantises a plain checkpoint and that the prefill GEMMs run on the INT8 tensor cores; its costs are that the weights are kept in both layouts (about one byte per weight, the memory of INT8 rather than of INT4), the quantisation is round-to-nearest (no GPTQ; perplexity of the 0.5B 23.7 against 20.5 with GPTQ), and it was tested on vLLM 0.25.1 and 0.34.0 (torch 2.14; same text, the same speed: 0.5B prefill 37370 tokens/s against 33998 for Marlin, decode 252 / 3911 against 300 / 4481; all the W4A8, checkpoint and plugin tests pass, slow ones included). Tests: test/E2E/test_w4a8_op.py (both paths against the dequantised reference, torch.compile(fullgraph=True), generation under vLLM with QUANTFORGE_SLOW_TESTS=1).

Hadamard rotation of W4A8 (new in 0.5.0)#

INT8 per-token activation quantisation is hurt by outlier channels, and 4-bit weights by outlier weights. Both are fixed in the same way as in QuaRot / SpinQuant: multiply the input by an orthonormal matrix B (block diagonal, one 128 x 128 Walsh-Hadamard block per group of 128 inputs) and the weight by the same, (x B)(W B)^T = x W^T, so the layer is unchanged in exact arithmetic but both operands are flatter when they are quantised. Here W B is computed once when the weights are quantised (online at load, or in GPTQ with the Hessian rotated to B^T H B), and the activation side costs one pass over the activations: inside the INT8 quantisation kernel above 64 rows (quantize_rows_rot: the rotated row waits in shared memory for its scale, bit-identical to rotating and then quantising), as a small kernel below. 2-4 % of the decode step at 1-64 requests, 1-2 % above.

What the simulation says and a rotation of 128 does not: the damage done by the INT8 activations (+0.42 / +0.63 on the two models) all but disappears (+0.01 / +0.04 on top of the rotated W4 weights); the effect on the 4-bit weights themselves depends on the block size without a clear rule (1.5B, W4 only: no rotation 13.512; blocks of 16 / 32 / 64 / 128 / 256: 13.550 / 13.710 / 13.184 / 13.600 / 13.540), so the block was fixed at 128, the group size of the kernels, rather than tuned on this model. quantization="quantforge_w4a8" rotates by default; quantforge_w4a8_plain is the old method (a different name because vLLM's compile cache is keyed by it, a switch that changes the graph must not be an environment variable); a rotated checkpoint says "rotated": true in its quantization_config. Not applicable to the GPTQ / AWQ W4A16 checkpoints of other people (their weights are not in the rotated basis). The Llama-3.2-3B failure is one layer: the input of the down_proj of layer 1 has a token 530 times the median norm (a massive activation, the attention sink) and the rotation, which spreads that single channel over its block of 128, raises that layer's output error from 0.054 to 0.080 and the model's perplexity by 1.1 (rotating only that down_proj gives 17.71, rotating everything else 16.74). Nothing in the weights flags such a layer (column norms are ordinary), so the online method, which has no activations, leaves the down_proj of the first four decoder layers unrotated (vllm_plugin._early_down_proj): the seven models above are the evidence for that rule, not a proof for other families. Quantising with GPTQ has calibration data, so there the decision is made per layer (gptq._rotation_helps: the output error of the rotated and the plain quantisation on a few tokens of every window, including the one of largest norm) and the layers that stay plain are listed in config.json (unrotated_layers; Llama-3.2-3B: layer 1 down_proj and layer 23 o_proj): GPTQ W4A8 of Llama-3.2-3B 16.537 plain, 16.377 with the per-layer decision.

Groups of 64 (quantization="quantforge_w4a8_g64" online, or make_w4a8_checkpoint.py --group 64, the checkpoint carries "group_size": 64): the integer group scale of the format (1..16) is its coarse part, and halving the group helps: Qwen2.5-1.5B online 13.395 -> 13.186; GPTQ checkpoint 12.331 -> 12.253 (the calibrated weights gain less). The INT8 kernel pays 2-3 % for the doubled scale / zero-point traffic (vLLM, 1.5B GPTQ checkpoint, tokens/s at 1 / 16 / 64 / 128 / 256 requests: 131 / 1958 / 5727 / 7390 / 9114 for group 128 against 128 / 1909 / 5624 / 7270 / 8964 for group 64, Marlin 131-141 / 1933-2090 / 5439-5847 / 7043-7242 / 7796-7875 in the two runs, which are noisy). Group 128 stays the default; groups of 32 compile and are exact but cost 4-10 % (CHANGELOG).

Measured on two Qwen2.5 sizes and OLMo-2 1B only; speed at 128 requests and below is 3-4 % under the unrotated W4A8 (the table above).

W4A8 checkpoints for vLLM (GPTQ quality, loads in seconds)#

benchmarks/make_w4a8_checkpoint.py <model> <out_dir> --train <wikitext-2 train parquet> quantises a Hugging Face model with the GPTQ of this format (quantize_model_gptq(..., fmt="w4a8"); --rtn for round-to-nearest; --rotate for the Hadamard rotation, decided per layer; --group 64) and writes it with quantforge.w4a8_checkpoint.save_w4a8: per decoder linear layer weight (int8 [N, K/2], the pack_k8 layout), group_scale / group_zero (int8 [N, K/128]), w_scale (f32 [N]), everything else dense fp16, and quantization_config = {"quant_method": "quantforge_w4a8"} in config.json. LLM("out_dir", quantization="quantforge_w4a8") then loads the quantised tensors as they are (the loader shards them like any other layer): no fp16 copy, no round-to-nearest step. Qwen2.5-3B (GPTQ, perplexity 12.54 against 13.47 for the online round-to-nearest): 1.99 GiB, loads in 2 s (25 s online), prefill 6678 tokens/s, decode 65 / 994 at 1 / 16 requests (compact mode), the same speed as the online path. The first-token log-probabilities of vLLM and of the Hugging Face model the checkpoint came from agree to 0.001 (test/E2E/test_w4a8_checkpoint.py, slow tests with QUANTFORGE_SLOW_TESTS=1). Every decoder linear layer must have sizes that are multiples of 128; the layout is format_version 1.

A 7 B model fits the 6 GB card too, from a bitsandbytes NF4 checkpoint (benchmarks/hf_bnb_to_quantforge.py dequantises each Linear and re-quantises it to uniform INT4, layer by layer in place, since NF4's non-uniform code cannot be fed to an INT4 GEMM): Mistral-7B-Instruct-v0.3 has wikitext-2 perplexity 8.366 under bitsandbytes and 8.506 under QuantForge (the extra 0.14 is the second quantisation), 4.2 GB of GPU memory (4.8 GB peak), coherent generation. Its batch-1 decode matches bitsandbytes' own NF4 kernel: 37 vs 38 tokens/s with HF generate (CUDA graph: 36). One decode step is 29 ms of GPU time: the fused gate/up GEMM (4096 → 28672) 13.8 ms, o_proj + down_proj 7.6 ms, q/k/v 2.7 ms, the fp16 lm_head 2.1 ms and 1400 small non-GEMM kernels 2.9 ms; at 180 GB/s the weights alone would take 22 ms. Profiling that step found that the K tile of the default decode schedule matters for wide layers (128 beats 64 by 18 % at N = 14336 and 28 % at N = 28672, loses by 10–15 % at N <= 6144), now chosen by the output width (32 → 36 tokens/s); an occasional 1.4 ms outlier in a 0.4 ms kernel is another process sharing the GPU.

The kernels reproduce the dense INT4 reference to 0.004 perplexity (logits top-1 agreement 99.6–100 %); the gap to fp16 is the round-to-nearest quantiser's. The 3 B and 3.8 B models only run quantised on this card: 3.1 / 3.2 / 2.6 GB of GPU memory at peak (their fp16 weights are 5.6 – 7.3 GB). Phi-3.5's CUDA-graph capture fails inside Hugging Face's LongRoPE code (a data-dependent if on a GPU tensor), not in the kernels; its numbers above are from generate. Models with a fused qkv_proj / gate_up_proj (Phi-3) are handled, models whose in_features is not a multiple of 128 are rejected.
