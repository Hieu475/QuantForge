Runtime and PyTorch op

Host side, compile cache, row buckets and the launches around the GEMM.

As a PyTorch op#

import quantforge.torch_ops                       # registers torch.ops.quantforge.w4a16_gemm
y = quantforge.torch_ops.w4a16_linear(x, packed, scale, zero_point, group_size=128, bias=b)
# x: f16 [..., K]  ->  y: f16 [..., N] (f32 accumulation); also works under torch.compile

The op is a torch.library.custom_op (fake implementation included), is covered by opcheck, torch.compile(fullgraph=True) and CUDA-graph capture/replay (test/E2E/test_torch_op.py). The op is registered by a small C++ extension (runtime/torch_runtime.cpp, built on first import in about 10 s and cached by torch; QUANTFORGE_NO_CPP=1 or a failed build falls back to the Python implementation) that keeps the whole call in C++ and calls back into Python only to compile a new shape or for the uncommon cases (K / N padding, per-tensor parameters, unaligned tensors). Kernels are compiled for a row bucket (≤ 16, 64, 128, 256, 384, 512, … 4096, then multiples of 1024; the activations are zero-padded to the bucket) on first use, so 24 different prompt lengths need 9 kernels, and the compiled libraries are kept in ~/.cache/quantforge/kernels (key = IR + options + tool binaries + shim source; QUANTFORGE_KERNEL_CACHE relocates it, QUANTFORGE_NO_KERNEL_CACHE=1 disables it): a restarted server compiles nothing (the test suite takes 4 s instead of 46 s on a warm cache). Kernels are compiled per shape and cached; warm each shape up once before capturing a graph (module loading is not allowed during capture). set_autotune(True) tunes the tile options per shape instead of using the default decode schedule. Measured 4096 × 4096, weights L2-resident (8 MB < 24 MB L2): op ≈ 52–61 µs per call (eager or graph) against Marlin's 19–25 µs — with the L2 warm the QuantForge kernel (~43 µs) is latency-bound, Marlin is not. With the weights streamed from DRAM (a real model has far more weight than L2) the kernel is faster than Marlin (table above); the extra small kernels around it (output init, f16 conversion, M < 16 padding) cost a few µs.

The generated kernels issue 16-byte vector loads on the packed weights, scales and zero points: those tensors must be 16-byte aligned (cudaMalloc / PyTorch allocations are; the harness raises on interior views).

The whole lowering is described in python/quantforge/PIPELINE.md (stages, every option, measured effect of each optimization).

Runtime (host side)#

python/quantforge/runtime/mgpu_cuda_runtime.c implements the mgpu* calls of the generated host code on the CUDA driver API. The PTX module is JIT-compiled once and cached by the address of its embedded image; W4A16Gemm.run hands it PyTorch's current stream (mgpuSetStream), the stream is neither created nor synchronised per call, so a call is an ordinary asynchronous op ordered after the caller's pending work. Per-call wall time of run (1 × 4096 × 4096, group-wise): 211–272 µs before, ~45–50 µs now (kernel ~50 µs). An M < 16 call only pads the activations and the output (the weights, scales and zero points are not copied).

Compile cache and row buckets#

compile_ir publishes libqf_kernel.so + lowered.mlir under ~/.cache/quantforge/kernels/<key>/ (atomic rename, safe for concurrent processes); the key hashes the IR, the target and pipeline options, the path / size / mtime of quantforge-opt, mlir-translate and llc, and the source of the CUDA shim, so a rebuilt compiler never serves a stale kernel. A compile takes ~0.3 s for a decode kernel (more for large prefill tiles); a hit costs a file read. torch_ops additionally maps the row count of a call to a bucket (bucket_rows) so that a server sees a handful of kernels per layer shape, not one per prompt length; rows above the real M are zero activations and are dropped.

Launches around the GEMM (torch op)#

A call with M < 16 rows used to launch: pad the activations (at::constant_pad_nd = allocate + fill + copy), the GEMM, the f32 -> f16 conversion of the result (and, before the overwrite kernel, a zeroing of the accumulator). The C++ hot path now copies the rows into a reusable zero-initialised [Mp, K] buffer (one launch; stale rows past M are harmless because a GEMM row only reads its own activation row, tested with NaN / inf poison), and the kernel overwrites its output. What remains is three launches per Linear. Removing the other two was measured to be worth little (a fused QKV and gate/up already cut the number of Linears per layer from 7 to 4) and costly: no pad needs the kernel to read only M activation rows (cp.async with a source size of 0 for the missing rows, one kernel per M; reading them unpadded faults with illegal address), and no convert needs an f16 output memref with an f32 accumulator, which the tensor-level IR cannot express without a temporary.
