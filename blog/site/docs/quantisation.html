Quantise a whole model#

import torch, quantforge.nn as qnn
from transformers import AutoModelForCausalLM

model = AutoModelForCausalLM.from_pretrained("Qwen/Qwen2.5-1.5B-Instruct", dtype=torch.float16)
stats = qnn.quantize_model(model, fmt="int4", group_size=128)   # int4 | int8 | fp8, RTN, layer by layer on the GPU
qnn.quantize_model(model, "int8", only=("lm_head",), fuse=False)  # optional: a lossless INT8 head (+2-16 % decode)
out = model.generate(ids.cuda(), max_new_tokens=64)             # the Linears are QuantLinear modules now

quantize_model replaces every nn.Linear (the lm_head stays dense unless asked) with quantforge.nn.QuantLinear, fuses q / k / v into one GEMM and a SiLU-gated MLP into gate + up (swiglu epilogue) for Llama / Qwen / Mistral style blocks, and works under torch.compile and CUDA graphs. Layers whose in_features is not a multiple of the group size fall back to 64 / 32 / 16 (else stay dense). QuantLinear.from_quantized(packed, scale, zero, ...) wraps GPTQ / AWQ tensors converted with quantforge.quant.

Real AWQ / GPTQ checkpoints go through load_quantized_checkpoint (4-bit, group-wise; desc_act act-order GPTQ is handled with a row permutation, zeros_offset=0 for gptq_v2):

model = AutoModelForCausalLM.from_pretrained("Qwen/Qwen2.5-0.5B-Instruct", dtype=torch.float16)   # the architecture
qnn.load_quantized_checkpoint(model, "Qwen2.5-0.5B-Instruct-GPTQ-Int4/model.safetensors", method="gptq")

The embeddings and norms are copied from the checkpoint as well (AWQ folds its activation scales into the norms, so the dense base model's norms are not the right ones). Checked against a dense twin (same dequantised weights in nn.Linear) with benchmarks/hf_load_checkpoint.py, wikitext-2 16 x 512: Qwen2.5-0.5B GPTQ-Int4 ppl 26.336 vs 26.335, 59/59 greedy tokens identical, 182 tok/s CUDA-graph decode; AWQ ppl 26.689 vs 26.689, 59/59, 184 tok/s; TinyLlama-1.1B-Chat GPTQ with desc_act=True (TheBloke; all 154 layers act-ordered) ppl 17.259 vs 17.259, 60/60 greedy tokens; a real FP8 checkpoint (RedHatAI/Qwen2.5-0.5B-Instruct-FP8-dynamic, method="fp8", per-channel scales expanded to group 128) ppl 22.543 vs 22.543 for its twin and 22.441 for the fp16 base model (greedy decoding diverges after 28 of 59 tokens: near-ties flip under the different fp16 rounding of the twin's matmul; the logits agree to 99.4 % top-1). Example with perplexity and decode speed: benchmarks/hf_quantize_model.py (RTN INT4, group 128, INT8 head). --compile (torch.compile of the quantised model before the CUDA-graph capture, which fuses HF's norm / rotary / elementwise kernels) adds ~10 % on the 0.5B model (206 -> 226 tok/s, 86 of 96 greedy tokens identical: fp16 rounding differs), 4 % on Qwen2.5-1.5B (97 -> 101) and 3 % on Llama-3.2-1B (142 -> 146); the share of those kernels shrinks as the GEMMs grow.

(RTN INT4 costs 2-4 perplexity points on these models; quantise with GPTQ / AWQ and wrap the result with QuantLinear.from_quantized for a better quality.) Layers are quantised in row chunks, so the 150k-row lm_head of a 3B model needs no fp32 copy of itself on the GPU.

Better 4-bit quality: GPTQ in the library#

import quantforge.gptq as qgptq
calib = qgptq.calibration_ids(tokenizer, train_text, nsamples=128, seqlen=512)    # [128, 512] token ids
qgptq.quantize_model_gptq(model, calib, group_size=128)                          # INT4, replaces RTN
qnn.quantize_model(model, "int8", only=("lm_head",), fuse=False)                  # lossless INT8 head

Sequential GPTQ (Hessian of every Linear input from the already quantised blocks, column-wise error compensation through the Cholesky factor of H^-1, scales rounded to f16 before the error is propagated, calibration token norms capped at 10x the median, see below). 49 s for Qwen2.5-0.5B, ~150 s for 1.5B, 300 s for 3B on the RTX 4050. Wikitext-2 perplexity on the whole test split (564-584 windows of 512 tokens; calibration: 128 x 512 tokens from the first 20 000 rows of the train split; INT8 head; benchmarks/hf_gptq.py --nseq 0 --fp16):

model fp16 RTN INT4 GPTQ INT4 share of the RTN loss recovered
Qwen2.5-0.5B-Instruct 18.79 22.91 20.45 60 %
Qwen2.5-1.5B-Instruct 12.66 14.30 13.38 56 %
Llama-3.2-1B-Instruct 17.91 22.28 20.21 47 %
OLMo-2-0425-1B-Instruct 17.24 19.02 18.13 50 %

A pitfall that the first version of this table hid. On 8 test windows GPTQ looked better than RTN everywhere; on the whole test split it was worse than RTN on Llama-3.2-1B (24.08 against 22.28) and recovered only 24 % on Qwen2.5-1.5B. benchmarks/ppl_per_window.py showed GPTQ better than RTN in 83 % of the windows but with a few windows completely broken (loss 9-10 per token instead of ~3), and a layer-by-layer comparison traced it to layers.1.mlp.down_proj: the layer that creates the "massive activation" of the attention-sink token (its input has a token 675x the median norm in Llama-3.2, 790x in Qwen2.5-1.5B). That token dominates the Hessian and the error compensation then damages other tokens. Capping every calibration token's norm at a multiple of the median before it enters the Hessian (token_clip) fixes it. A cap of 30 fixed the whole-split perplexity (Llama 20.12) but a slow regression test on the windows that had been broken (test/E2E/test_gptq_real_model.py) showed one still broken (window 70: loss 5.9 against 3.0 for fp16); a per-window analysis of all 564 windows found no window worse than round-to-nearest at a cap of 10 (30: two windows, one by 2.8 nats; 5: none, but 0.2 ppl worse), so 10 is the default (token_clip=10; cost: ~0.07 ppl against 30). Quantising just the massive-activation layer with RTN also fixes Llama, but hurts Qwen-0.5B, so a fixed list of layers does not work. Options that did not help consistently, hence off by default: clip=True (per-group range shrinking), act_order=True (the layers lose the q/k/v fusion), larger damping, more calibration windows.

INT8 W8A8 (the INT8 tensor cores: 2.0x in hardware, lost around the GEMM)#

quantize_model(model, "int8_w8a8") (INT8W8A8Linear, cuBLASLt torch._int_mm, column-major B). Measured on the RTX 4050: the INT8 mma peaks at 88.2 TOPS against 44.1 for fp16 (benchmarks/mma_peak.cu, the instruction LLVM 18 can emit, unlike FP8), cuBLASLt reaches 80-83 TOPS against 37-38 TFLOP/s (a row-major B silently falls to 24 TOPS), but whole-model prefill is 0.90x (Qwen2.5-0.5B) and 1.07x (Llama-3.2-1B) of fp16 because the activation quantisation and the scale epilogue cost about as much as the saving; perplexity +0.33 to +0.41 on wikitext-2. A kernel generated by the compiler with those two fused is the open path to beat cuBLAS fp16 at prefill (about 1.8x for large layers by the arithmetic of the blog post); it is not built.

A compiler-generated INT8 GEMM (experimental). quantforge.e2e.Int8Gemm compiles C[int32] = A[int8] @ Bt[int8]^T through the existing pipeline onto the INT8 Tensor Cores (mma.m16n8k32.s8; options thread-tile-k=32 smem-pad=16 accumulate=false, block-swizzle=16 for weights larger than the L2). Bit-exact against cuBLASLt for all 129 schedules of a sweep, 59-65 TOPS on large shapes (instruction peak 88, cuBLASLt 70-78) and 1.1-1.7x cuBLAS fp16 on every shape tried (benchmarks/int8_gemm_probe.py). Int8GemmDq adds epilogue=int8-dequant: the dequantisation y[f16] = (A @ Bt^T) * sx[m] * sw[n] + bias[n] is folded into the GEMM's stores, one kernel, no int32 intermediate (bit-exact against the f32 reference; 1.29-1.81x cuBLAS fp16 for the whole GEMM + dequantisation). quantize_model(model, "int8_w8a8") uses it (INT8W8A8Linear, per-token activation scale, per-channel weight scale): whole-model prefill of 2048 tokens is 1.10x (Qwen2.5-0.5B), 1.18x (Llama-3.2-1B) and 1.20x (Qwen2.5-1.5B) of fp16 (the cuBLASLt route was 0.91-1.08x), wikitext-2 perplexity +0.33..0.41. The layer GEMMs are 1.46x faster; 28 % of the fp16 prefill is the element-wise ops of an eager Hugging Face model, the head stays fp16 and the activation quantisation costs 7.6 ms (profile in the blog). q/k/v and gate/up share one quantisation and one GEMM (1-3 %), and silu(gate) * up + the per-token quantisation of down_proj's input is one compiled function (_silu_mul_quantize; perplexity unchanged to 0.01): 8-14 % faster than without it; the RMSNorm in front of q/k/v and gate/up also quantises its own output (one compiled function returns the fp16 output and the int8 values + scales, _install_norm_quantisation; 5-10 % more). Whole-model prefill of the three models: 1.37x / 1.46x / 1.49x of eager fp16 (90.0 / 184.6 / 239.7 ms), or 1.28x / 1.34x / 1.43x of fp16 with compiled RMSNorms (84.3 / 169.6 / 229.1 ms: compiling the norms alone is worth 4-9 % for fp16 too, so that is the fairer baseline); perplexity unchanged (+0.006 at most). block-swizzle=8 only pays for a weight larger than the L2 (2.3x there, 12-14 % slower below). It needed an integer extension-folding pattern in the vectorization pass, the thread-tile-k option, an i32-aware overwrite pass, a fix to the shared-memory promotion pass (a transposed B tile was only recognised when block N equalled block M: half the output or more was wrong for the other block shapes; the sweep that compared every result with cuBLASLt found it) and the new epilogue kind.

W4A8 (INT4 weights, INT8 activations, experimental). quantize_model(model, "w4a8") (W4A8Linear, kernel quantforge.e2e.W4A8GemmDq): QServe-style progressive quantisation (INT8 per channel, then INT4 per group of 128 with an integer scale and zero point), so the tensor cores get (nibble - zero) * scale as int8 built while the tile is staged, the accumulation is one int32 over K and the only float scale is the per-channel one of the int8-dequant store: one kernel, no compiler change (the weight is a linalg.generic the producer-fusion pass recomputes at the loads; python/quantforge/PIPELINE.md). Kernel: 1.30-1.48x cuBLAS fp16 and 1.45-2.20x the QuantForge W4A16 kernel at 2048 rows (55-63 TOPS), 6-21 % behind the INT8 kernel (benchmarks/w4a8_gemm.py). Whole-model prefill (2048 tokens, with the fused silu * up and norm quantisations below): 1.23x / 1.26x / 1.34x of fp16 with compiled norms for Qwen2.5-0.5B / Llama-3.2-1B / Qwen2.5-1.5B (INT8: 1.30x / 1.33x / 1.43x; before the packed dequantisation pass 1.16x / 1.22x / 1.28x; 1.03x / 1.07x / 1.10x without the fusions) against 0.83x / 0.88x for INT4 W4A16, at INT4 quality (perplexity 23.7 / 22.1 against 22.9 / 22.3 for W4A16 RTN; 14.7 against 12.7 for fp16 on the 1.5B) and the smallest memory (0.47 / 1.05 / 1.19 GB against 1.01 / 2.48 / 3.10 for fp16). INT8 W8A8 is faster (1.37-1.49x of eager fp16) and closer to fp16 when the memory is affordable. On Qwen2.5-3B (about 6 GB in fp16: it does not fit this 5.6 GB card; set PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True, fragmentation otherwise runs the benchmark out of memory) W4A8 prefill of 2048 tokens takes 356 ms in 2.07 GB against 498 ms in 2.25 GB for INT4 W4A16 (1.40x), INT8 W8A8 310 ms in 3.42 GB; wikitext-2 perplexity RTN / GPTQ: W4A8 13.47 / 12.54, INT4 W4A16 13.13 / 12.06, INT8 12.15. Prefill / large-batch format (fewer than 17 rows use a dequantised fp16 matmul); needs in/out features that are multiples of 128; quantforge.gptq.quantize_model_gptq(model, ids, fmt="w4a8") adds GPTQ (wikitext-2 perplexity, fp16 head, RTN -> GPTQ: Qwen2.5-0.5B 23.7 -> 21.1 (INT4 W4A16 GPTQ 20.5), Llama-3.2-1B 22.1 -> 19.9 (20.2), Qwen2.5-1.5B 14.7 -> 13.7 (13.4); benchmarks/w4a8_gptq.py; no act-order). The first version used a symmetric range and was 5 perplexity points worse than INT4: the group zero point matters (blog, update 5).

FP8 W8A8 on the Ada FP8 tensor cores (a negative result, for now)#

quantize_model(model, "fp8_w8a8") replaces the Linears with FP8W8A8Linear: FP8 E4M3 weights and activations (per-output-channel weight scale, dynamic per-token activation scale) through torch._scaled_mm (cuBLASLt) on the FP8 tensor cores of sm_89, which are 1.9-2.1x faster than the fp16 ones for a bare GEMM on this card (72-77 against 37-38 TFLOP/s sustained; an earlier version of this document said 1.8-2.6x from an fp16 baseline measured before the GPU reached its sustained clocks). It is not generated by the QuantForge compiler (LLVM 18 cannot emit the FP8 mma). Quality is good (Qwen2.5-0.5B wikitext-2 perplexity 19.10 against 18.79 for fp16 and 22.91 for INT4 RTN; Llama-3.2-1B 18.13 against 17.91), but the speed is not: whole-model prefill of Qwen2.5-0.5B takes 117 ms for 1 x 2048 tokens against 108 ms in fp16 (0.92x; per-tensor scales: 103 ms, but 326 against 214 ms for 8 x 512), because the quantise / rescale passes around the GEMM cost as much as the GEMM saves at these layer sizes (benchmarks/hf_fp8_w8a8.py). Per layer the speed ranges from 0.35x to 1.5x of fp16 depending on the shape. A speed-up would need the activation quantisation and the scale epilogue fused into the GEMM (a compiler job). Use it for the 2x smaller weights and the quality, not for speed.
