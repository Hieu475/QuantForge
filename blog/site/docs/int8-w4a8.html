Integer tensor cores: the int8-dequant epilogue and packed W4A8 dequantisation.

INT8 GEMM (experimental)#

i8 x i8 -> i32 goes through the same pipeline as the W4A16 kernels (linalg.matmul_transpose_b, B as [N, K]: ldmatrix cannot transpose 8-bit data). What it needed: FoldExtSIIntoContract in quantforge-vectorization (the vectorised matmul is contract(extsi a, extsi b, acc); LLVM 18 folds only extf), the pipeline option thread-tile-k (32 selects mma.m16n8k32; 16 would give m16n8k16, which is no faster than f16), smem-pad=16 (a row of an int8 tile must stay 16-byte aligned for ldmatrix) and i32 support in quantforge-overwrite-output. Schedule: quantforge.e2e.INT8_GEMM_OPTS (best of 129 exact combinations). SharedMemoryPromotionPass::isTileSizedSubview recognises operand tiles by shape ([M-tile x K], [K x N-tile]); a transposed B is [N-tile x K] and used to be found only when block N happened to equal block M / warp M, otherwise the warp tile was promoted into a buffer shared by all warps (wrong results for 48 of 180 combinations); [N-tile x K] is accepted now, and test/E2E/test_int8_gemm.py covers the combinations that failed.

epilogue=int8-dequant#

The program is matmul_transpose_b (i8 -> i32) followed by a linalg.generic (quantforge.no_tile, quantforge.no_vectorize) computing y = f16(c * sx[m] * sw[n] + bias[n]); the function arguments are tagged quantforge.int8_row_scale / int8_col_scale / int8_bias / int8_out. quantforge-fuse-epilogue{kind=int8-dequant} (after the overwrite pass) rewrites every vector<2xi32> accumulator store of the GEMM kernel: the pair is converted (sitofp, two multiplies, bias, truncf) and stored to the f16 output at absolute coordinates with ONE 4-byte st.global.b32 (inline asm; the generic lowering of a vector<2xf16> store gave two 2-byte stores). The elementwise kernel (every other gpu.launch that touches the int32 buffer), the dead subviews and the buffer's gpu.alloc / gpu.dealloc are erased: the device allocation matters, a first version left it and every call did a cudaMalloc of M x N x 4 bytes (device time 1.1 ms, wall time 2.1 ms; ncu said the kernel was fine, the profiler's device time versus the wall time per launch said where the second millisecond was).

W4A8 (W4A8GemmDq): a plain linalg.generic as the weight producer#

INT4 weights with INT8 activations need no new pass: the program is a linalg.generic (quantforge.no_tile, quantforge.no_vectorize) that builds the int8 weight Bt[n, k] = (nibble(Bp[n, k floordiv 2], k mod 2) - zp[n, k floordiv 128]) * gs[n, k floordiv 128] (all i8 arithmetic; the packed byte, scale and zero point are read with tensor.extract at k divui 2 / k divui 128, not through affine maps with floordiv: those expand to signed floor-division sequences that quantforge-simplify-index-math cannot fold, so the byte loads stayed scalar ld.global.u8 (80 per tile instead of 16 ld.global.u32; -7 % time)) followed by the matmul_transpose_b and the int8-dequant generic above. After bufferisation the producer is a standalone elementwise kernel writing an [N x K] int8 buffer, and the existing quantforge-fuse-producer-into-loads pass (it is not specific to qf.dequant: any store whose backward slice is pure and reads only inputs) recomputes it at the loads that stage the B tile and deletes the kernel and the buffer, so the 4-bit weights are the only weight traffic and the whole GEMM + dequantisation is one kernel (w4a8_gemm_dq, 1 launch in the profiler). The accumulation is int32 over all of K: the group scale is an integer and is folded into the int8 weight before the mma, the only float scale is per output channel and lives in the epilogue (QServe's progressive quantisation). quantforge.quant.w4a8_quantize picks (gs, zp) per group by minimum squared error among the pairs for which (q - zp) * gs stays inside int8, because the kernel's 8-bit arithmetic wraps. Cost: the dequantisation (and, per row block, its repetition) is ALU work in the main loop, 50-58 TOPS against 59-72 for the int8 kernel (ncu: 3.7x the instructions of the int8 kernel, issue-bound; the 8-bit arithmetic is still done in 16-bit registers and re-packed with bfi: a SWAR form on the loaded 32-bit word, as quantforge-vectorize-dequant does for the f16 path, is the next step and would be worth about 3 % of whole-model prefill).

Packed W4A8 dequantisation (quantforge-vectorize-dequant, pack_k8 layout)#

The W4A8 nibbles are stored so that no byte permutation is needed to unpack them: in each block of 8 consecutive k, byte j holds element j (low nibble) and element j + 4 (high), so w & 0x0F0F0F0F of a 32-bit word is four consecutive elements and (w >> 4) & 0x0F0F0F0F the next four (quant.pack_k8). The producer is written so that the index arithmetic simplifies completely (divui / remui only, the group index taken from (k / 16) * 16, or / 8 for the 8-wide f16 items of the decode kernel, so that the (scale, zero point) loads of one work item are ONE value; a signed floordiv or k & 4 defeats quantforge-simplify-index-math). quantforge-vectorize-dequant then recognises the 16 scalar trees (nibble - z) * s of a vector<16xi8> store and emits 32-bit word arithmetic: word * s (a nibble times s <= 16 is at most 240: no carry between bytes) and the zero point subtracted per byte with ((x | H) - (y & ~H)) ^ ((x ^ ~y) & H), H = 0x80808080: about 10 instructions per four elements instead of ~30, bit-identical (mod 256). The f16 decode variant (vector<8xf16>, mulf(sitofp(nibble - z), s)) uses the magic-number form of the W4A16 path (1152 + q, sub.f16x2, mul.f16x2). FileCheck: test/Transforms/vectorize_dequant_w4a8.mlir. A scalar-load extension of quantforge-prefetch-weight-loads (the scale / zero point memref.loads) was tried for the decode kernel and gave nothing: reverted.
