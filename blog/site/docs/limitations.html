Limitations#

  • Speed: the W4A16 kernels are on par with Marlin up to 16 rows and 0.90-0.92x of it in vLLM prefill (0.9-1.04x at the GEMM level for 384-2048 rows), 0.8-0.9x at 32-256 concurrent rows of decode (the table above was measured at the start of the work; the tile planners, 32-row buckets and split-K added later raised the end-to-end ratios, see "Headline results" and the CHANGELOG): there the GEMM is compute bound and the compiler's mma loop reaches ~29 of the 44 TFLOP/s the hardware peaks at (Marlin ~37). The gap is not DRAM, tile choice or dequantisation arithmetic (ablated); a hand-written CUDA prototype that keeps B in registers like Marlin reaches 33-36 TFLOP/s when balanced (PIPELINE.md), closing it needs that layout (a change of the weight format), which is not done. The W4A8 path (INT8 tensor cores, measured schedules) is what beats Marlin from ~64 rows of GEMM and from 128 concurrent requests end to end (1.04 / 1.13 / 1.18x at 128 / 192 / 256), at W4A8 quality; at 1-32 rows of one GEMM it is 0.8-1.0x of Marlin (the INT8 kernel itself is on par; the activation quantisation and, at 1-16 rows, the decode kernel cost the rest).
  • W4A8 rotation: measured on Qwen2.5 (0.5B, 1.5B), OLMo-2 1B, Phi-3.5-mini and Llama-3.2 (1B, 3B) only; it is not a free win (rotated everywhere, Llama-3.2-3B gets 1.1 perplexity worse because of one massive-activation layer) and the online method relies on a rule (the down_proj of the first four layers stays unrotated) that seven models support, not prove. Use quantforge_w4a8_plain as the reference when trying a new family; the GPTQ path decides per layer from calibration data.
  • MoE: 4-bit silu-gated experts only, one model run end to end (see "Mixture-of-experts models"), 0.93-0.96 of Marlin MoE at 1-32 concurrent requests, 0.88 in prefill. Not supported: expert parallelism, AMD / Apple GPUs, GPUs older than sm_80, tensor-parallel runs were not tested on more than one GPU, act-order layers cannot be written by save_gptq. Only one GPU model was measured; the planners measure per GPU, a pack built on one GPU carries its decisions (other GPU models fall back to the rule-based schedules without a compiler).
  • Schedules by rows: M ≤ 16 one 16-row decode tile, ≤ 32 / ≤ 64 skinny 32 / 64-row tiles, larger M 64 / 128-row tiles (the torch op buckets M and picks them; autotune searches them).
  • W4A16, W8A16 and FP8 (E4M3) weights with f16 activations (the torch op picks the kernel from the weight: packed INT4 [K, N/2], plain int8 [K, N], or a torch.float8_e4m3fn [K, N] from quant.quantize_fp8; 8-bit weights are group-wise only and have no fused swiglu, FP8 ignores the zero point). No NF4, no activation quantization (FP8 activations / FP8 tensor cores are not used). Act-order GPTQ (desc_act=True) works through quant.from_gptq_act_order (rows permuted offline, perm= in w4a16_linear gathers the activations: one extra small kernel per call). Zero points are stored unpacked (int8 [K/G, N]); AWQ / GPTQ checkpoints are repacked offline in Python (quantforge.quant). Besides round-trip tests against independent packers, real 4-bit checkpoints (Qwen2.5-0.5B-Instruct AWQ and GPTQ-Int4, group size 128, layers of shape 896 → 4864, 4864 → 896, 896 → 128, 896 → 896) are run through the kernels and compared with vLLM's AWQ dequantisation and an f32 reference built from the GPTQ file format (test/E2E/test_real_checkpoints.py: downloads a few MB with HTTP Range requests, skips offline). Real checkpoints are covered for desc_act=False and desc_act=True GPTQ, zero_point=True AWQ (GEMM version) and FP8-dynamic (weights only: 0.55 % of its bf16 scales are subnormal in f16).
  • Epilogue: bias and residual are fused by initializing the accumulator (run(bias=, residual=)); relu / silu / gelu (tanh form) are applied to the f32 accumulator before the store (build(epilogue="silu"), activation= in the torch op), i.e. act(bias + A @ W). A gated MLP is one GEMM: quant.interleave_gate_up interleaves the gate and up weights by column and epilogue="swiglu" stores silu(x @ Wg) * (x @ Wu) (activation="swiglu" in the op, output half as wide, no bias). accumulate=False makes any kernel write C = A @ W without reading C. Not fused: gelu-gated variants, residual after the activation, quantised output.
  • Tile-aligned static shapes in the compiler; other shapes work through zero-padding in the Python harness. The degenerate decode case of a single block (N = 64) is not fused into one kernel (correct, but two launches).
  • NVIDIA sm_80+ only (PTX is JIT-compiled by the driver); no Hopper wgmma/TMA.
  • The scalar FMA fallback (tensor-core=false) is correct but ~10× slower; LLVM 18's NVPTX backend miscompiles one variant of it (documented in PIPELINE.md).
  • Kernels are PTX loaded through a small CUDA driver shim (runtime/mgpu_cuda_runtime.c): the JIT-compiled module is cached and launches go on PyTorch's current stream, asynchronously like any other op (host cost ~45–50 µs per call from Python for a 4096 × 4096 decode GEMM, kernel ~50 µs; Marlin's launch is ~20–25 µs wall). The torch op's hot path is C++ (no interpreter per call); the Python W4A16Gemm.run still costs ~45 µs. The benchmark tables report device kernel time.

Repository layout#

path content
include/QuantForge, lib/Dialect the qf dialect (qf.unpack, qf.dequant with per-tensor / group-wise parameters)
lib/Transforms passes + --quantforge-gpu-pipeline (GPUPipeline.cpp)
tools/quantforge-opt mlir-opt-style driver (all upstream passes + QuantForge's)
python/quantforge e2e.py (compile + run harness), quant.py (group-wise quantization, AWQ/GPTQ repack), autotune.py, benchmark.py, smoke.py, CUDA runtime shim
test/Transforms, test/Dialect lit/FileCheck tests
test/E2E GPU tests: compile → run → compare with PyTorch
benchmarks/ recorded baselines (JSON, with environment) and compare_marlin.py
scripts/ check.sh, sanitize.sh
